## 2. 最小闭环的完成定义

一个任务只有同时满足以下完整路径，才算进入最小闭环：

1. 用户从任务列表新建任务；需求对话持续确认目标、对象、来源、范围、结果、动态词、风险和用户预期，所有会改变结果的重要歧义均由用户决定或明确委托。
2. 用户未提供 URL 时，访谈 LLM 根据完整对话决定搜索词并判断宿主返回的原始结果；宿主只校验候选引用，多个合理候选通过 Question Panel 由用户确认，不要求用户填写技术入口。
3. 用户发起一次“准备任务”；系统只负责规划、真实页面调查、预执行、编译和验证，不要求用户理解 E1-E4、selector、节点或 JSON；发现新的业务歧义时返回需求对话。
4. 系统需要补充不同输入或登录、验证码、授权现场时，以业务语言请求输入或进入人工等待。
5. 验证通过后，系统发布一个固定需求、计划和链路 digest 的运行版本，并保存合法的默认运行预设。
6. 任务在列表中明确显示“可运行”，用户可以直接点击“运行”，不必先进入任务计划页。
7. 每次点击都创建独立运行；运行中可以查看进度、调整人类可观察的执行节奏、停止，或在人工处理后恢复同一运行。
8. 链路沿合法控制流结束且没有节点、合同或运行时错误时，本次运行即完成；执行型任务显示完成回执，数据型任务显示业务结果。
9. 用户查看结果后可以接受、在自由画布修订局部节点，或携带本次运行记录返回需求对话；用户不满意不改写原运行完成事实。
10. 确定性失败允许用户明确授权模型修复；修复产生并验证新版本，成功后再发布，旧版本和历史运行不改写。
11. 关闭并重新打开工作台后，任务、当前可运行版本、默认预设、运行历史、待处理状态和修订草稿仍然一致。

“页面能动”“接口返回 202”“节点测试通过”或“用户最终能绕到计划页手工运行”均不构成产品闭环通过。

## 3. 本阶段明确不做

- 不建立账号、Cookie、Profile 或多身份管理中心；遇到登录、验证码和授权只请求人工并恢复同一运行。
- 不把网站入口、最新内容、页面路径、业务字段或弹窗文案写进平台代码；这些属于需求对话、预执行和版本化任务数据。
- 不新增第二套图调度器、公式语言、关键词任务分类器或运行时 Agent loop。
- 不做批量运营、定时任务、分享、云同步、权限协作、跨设备同步和通知中心。
- 不用 mock、fixture、类型检查或单个节点成功代替最终产品入口的真实验收。
- 不为完成本阶段重新设计整个工作台；保留现有 React、Radix UI、导航和主题，在其上完成清晰一致的产品层。

## 4. 产品领域模型

### 4.1 任务是唯一用户资产

用户管理的仍是现有“任务”，不是另建一个“链路项目”或“自动化脚本”。需求对话、准备过程、可运行版本、运行预设、运行历史和
修复历史都归属于同一任务。任务可以处于未确认、待准备、准备中、待补充、可运行、运行中、等待人工、需修复或已归档等状态。

### 4.2 可运行版本

可运行版本是一份不可变发布清单，至少固定：

- 已确认需求的 id、version、revision 和 digest；
- TaskPlan 的 id、version 和 digest；
- 每个计划步骤实际采用的 TaskChain id、version 和 executable digest；
- 发布时已经通过的样本与不同输入验证证据；
- 输入合同、结果形态以及创建时间。

“取数据库里最新的链”不能替代发布清单。候选修复和新验证不能在用户点击运行与执行启动之间静默替换版本。

### 4.3 运行预设

运行预设保存用户下次点击“运行”时采用的默认业务输入和执行节奏。它必须通过当前可运行版本的输入合同校验，并绑定该版本；
新需求或新运行版本发布后，旧预设只有重新校验通过才能迁移。预设不是 TaskChain 定义，不参与链路 digest，也不能改变节点语义。

### 4.4 可运行任务

可运行任务是任务、当前可运行版本和合法运行预设共同形成的产品投影，不是一个可以与原任务分叉的第二实体。只有该投影成立时，
链路运行台才显示直接运行操作；任务列表始终只负责选择和导航。

### 4.5 运行完成、执行回执与用户验收

- 运行完成：发布链路到达合法完成终点，所有实际执行节点和输出合同均无未处理错误；不再由链外语义 judge 改判。
- 执行型任务：主结果是运行完成回执和实际节点事实；没有伪造的数据 JSON。
- 数据型任务：主结果是满足 TaskPlan 输出合同的业务数据；执行回执作为审计信息单独展示。
- 等待、部分完成、阻断、失败和取消都有明确状态、原因、影响范围和下一步动作，不能统一显示为“运行失败”。
- 用户验收：用户独立判断实际结果是否符合预期，可选择接受、调整链路或重新梳理需求；验收意见不能改写运行历史。

### 4.6 执行生命周期与资源清理

- TaskRun 的链路运行结论来自实际节点、输出合同和 terminal；runner、浏览器和临时资源是否释放是独立清理结论。
- 链路完成而清理未确认时，TaskRun 继续是 completed，正式 execution 为 `cleanup_required`，产品只提供核验并清理资源，不提供模型修复。
- 清理确认后同一 execution 闭合为 completed；清理尝试和原始异常继续留在审计中。
- 业务失败与清理失败同时发生时，业务失败保持主因；清理完成后再恢复原业务下一步。
- 资源所有权未确认释放前不得开始占用同一浏览器资源的新运行，但不得通过重新生成链路规避该门。

## 5. 目标交互流程

### 5.1 新建与需求确认

- 新建任务后进入需求对话。
- 需求对话负责确认用户真正要得到的结果、对象、来源/服务范围、动态业务输入、结果形态、异常处理、风险和用户预期。
- 一轮只解决一个决策轴，但不得人为限制轮次。所有会改变结果的重要待决事项必须由用户确认或明确委托，未清零时不能生成可确认草稿。
- 用户提到站点或内容但没有 URL 时，访谈 LLM 决定只读搜索词并从原始结果中提交真实候选 ID；宿主不做语义排名，只校验引用并生成 Question Panel；无可靠候选或搜索不可用时保持待决。
- 用户确认业务来源、内容对象和动态选择规则，不填写 `startUrl`、selector、JSON 或内部合同；真实页面入口和控件由预执行在授权范围内调查。
- “最新、全部、前 N 条、正片、成功、完成”等词在影响结果时必须收窄为用户能审阅的含义。
- 草稿确认后，工作台主操作变为“准备任务”。

### 5.2 准备任务

点击一次“准备任务”即授权本轮规划、预执行、编译及验证所需的浏览器活动。界面只展示用户可理解的阶段：

1. 正在形成执行方案；
2. 正在用代表输入完成任务；
3. 正在生成可复跑链路；
4. 正在验证同样输入；
5. 正在验证复用边界；
6. 已可运行，或需要用户处理。

内部 E1-E4、模型审计、链路 gap 和节点证据保留在详情中，不作为主操作步骤。

准备任务只研究真实网页上的实现方法，不重新决定需求含义。页面结构、控件、标签页、等待、登录现场、输入输出绑定和技术路径由系统处理；
如果现场出现新的来源、范围、停止点、授权或结果含义歧义，准备 job 暂停并把一个业务问题送回需求对话，不允许探索模型替用户决定。

系统应从已确认需求形成代表输入。若无法安全确定不同输入验证样本，界面显示按 input contract 生成的业务字段表单，并明确说明
“此输入只用于确认同一任务在不同内容下仍可复用”；不得回退到原始 JSON 文本框。

### 5.3 任务选择与链路运行台直接运行

最近任务列表只承担任务选择、导航和状态摘要。点击整行立即显示选中态或加载反馈并打开对应工作区，不创建 execution，也不把列表行或 session 项暗中当成运行按钮。

任务被打开后，主操作出现在与当前阶段一致的工作区：

| 状态 | 工作区主操作 | 行为 |
| --- | --- | --- |
| 新需求 / 待确认 | 继续对话 | 打开需求对话 |
| 待准备 | 准备任务 | 打开准备说明并由用户启动 |
| 准备中 / 排队中 | 查看进度 | 打开当前准备状态；禁止重复派发 |
| 待补充验证 | 补充输入 | 打开业务字段表单 |
| 可运行 | 在链路运行台“运行” | 使用当前发布版本和默认预设创建独立 execution |
| 运行中 | 查看本次运行流 | 链路运行台绑定当前 execution，不显示第二个运行按钮 |
| 等待人工 | 去处理 | 在对应节点和顶部状态条显示“核验现场并恢复” |
| 待清理 | 核验并清理 | 保留链路结果，确认所属 runner、浏览器和临时资源释放后再允许运行 |
| 上次已完成 | 在链路运行台“再次运行” | 仍使用当前发布版本和默认预设 |
| 需修复 | 查看并修复 | 打开失败回执；修复必须再次明确授权 |
| 外部阻断 | 查看原因 | 不把访问限制误导为本地链路修复 |

任何异步操作必须在同一渲染周期显示 pressed/busy，随后显示 accepted、settled 或 error；不得点击后无任何动静。窄屏和触屏不能依赖 hover 才能看到主操作。

### 5.4 运行参数

- 无动态输入：点击链路运行台“运行”后直接排队。
- 有动态输入且预设有效：直接运行；用户可以在运行按钮旁选择“修改本次输入”。
- 预设缺失或因新版本失效：同一位置显示“配置并运行”，点击后立即打开业务字段表单，保存后再创建运行。
- 服务端接受后返回唯一 execution 引用，运行台自动绑定它并显示 queued/running；网络重试沿 requestId 返回同一 execution。
- 表单根据有限 ValueSchema 递归渲染 string、enum、number/integer、boolean、array 和 object；字段错误就地显示。
- JSON 只允许放在“技术详情/导出”中，不是正常产品入口。
- 执行节奏属于运行预设；使用带含义的档位和精确值说明，默认采用正常人操作节奏，并允许运行中调整后续节点。

### 5.5 人工等待

- 登录、验证码、权限确认或访问限制出现时，保存当前检查点并停止自动动作。
- 页面显示为何需要人工、需要用户做什么、属于哪次运行以及完成后的唯一操作。
- 用户点击“我已处理，核验并继续”后恢复同一 run；重新观察现场，不重复已经确认完成的副作用。
- 本阶段不管理登录态来源，但必须保证等待、取消、服务重启和恢复后的状态一致。

### 5.6 结果与回执

结果页首屏只回答三件事：实际运行了什么、是否存在真实执行错误、用户下一步能做什么。

执行型任务完成态显示：

- “运行已完成”的明确结论；
- 实际执行步骤、节点结果和输出摘要；
- 本次输入摘要、完成时间和“再次运行”。

数据型任务完成态显示业务结果；执行回执折叠为次级区域。所有任务的技术详情可展开查看 run id、运行版本、计划/链路 digest、
browserCommands、modelCalls、provider reportedInvocations、节点事实、产物和清理结果。

完成态同时提供“符合预期 / 调整链路 / 重新梳理需求”。“符合预期”不作为 completed 的前置条件；用户不满意时保存验收意见，
不能把原运行改写成失败。

失败态显示失败发生在哪个业务步骤、已完成范围、是否可能有副作用、证据和下一步。不得只显示异常字符串或一段完整 JSON。

链路步骤和输出已经完成、但运行资源清理未确认时，不使用失败态：首屏显示“任务步骤已完成，浏览器资源回收尚未确认”，保留业务结果，
主操作为“核验并清理资源”。此状态不显示确定性修复授权；清理确认后恢复 completed/rerun。

链路正常结束后不得追加来源 judge、完成态 judge 或通用证明引擎，仅因缺少额外语义证据把 completed 改成 failed。
准备代表执行必须关闭 browser-use 全局 judge；新 trace 不写 `judged`。历史完成 predicate 只作为版本审阅信息，不在 chain/step/plan 结束后成为第二套运行门；运行完成证据记录实际到达的 terminal。准备编译出现 `confirm_intent` 时必须持久化需求回流并返回需求对话。

### 5.7 修复

只有本地、确定性、可归属到任务链路的失败可以提供“授权修复”。认证、验证码、频控、访问拒绝、不确定网络状态和用户取消不进入修复模型。

修复入口必须：

1. 绑定失败 execution、run、步骤、节点、输入 digest、链路 digest 和相关证据；
2. 告知用户修复会调用模型并启动一次受控验证；
3. 产生新的不可变候选版本，不修改当前发布版本；
4. 重新经过样本与不同输入验证；
5. 全部通过后原子发布为新的当前可运行版本；
6. 保留旧运行版本、失败回执和修复审计。

用户认为结果不符合预期但运行本身没有真实错误时，不进入上述“失败修复”路径：

- 局部节点或连线不对：从当前发布版本创建链路修订草稿，在自由画布修改并验证，成功后发布新不可变版本；
- 目标、来源、范围、结果或风险理解错误：携带本次运行摘要返回需求对话，形成新需求版本后重新准备；
- 手动编辑链路不隐式调用模型；只有用户明确选择模型辅助修复时才产生模型用途和成本。

## 6. 状态投影规则

产品状态必须从已保存事实投影，不能另存一个容易漂移的 `ready=true`：

| 优先级 | 已保存事实 | 产品状态 |
| ---: | --- | --- |
| 1 | 当前需求对话正在生成 | 正在处理需求 |
| 2 | 当前准备/修复 job 排队、运行或等待人工 | 准备中 / 等待人工 |
| 3 | 正式 execution 排队、运行、暂停或等待人工 | 排队中 / 运行中 / 等待人工 |
| 4 | 当前确认需求没有发布版本 | 待准备或待补充验证 |
| 5 | 发布版本存在但预设缺失或不再满足输入合同 | 需要运行输入 |
| 6 | 最近正式运行存在未确认的资源清理 | 待清理；主操作为核验并清理，不显示模型修复 |
| 7 | 最近正式运行为可修复失败，且仍绑定当前发布版本 | 需修复 |
| 8 | 当前发布版本和预设均有效，最近正式运行完成且清理已确认 | 上次已完成，可再次运行 |
| 9 | 当前发布版本和预设均有效，没有正式运行或最近运行已取消 | 可运行 |
| 10 | 任务已归档 | 已归档，只读 |

同一时刻只能有一个主产品状态和一个主操作。样本/验证运行不应把任务列表状态投影为“正式运行已完成”。

## 7. 开发事项与顺序

以下顺序是产品闭环的最小实现，不允许只做 UI 外壳后用旧的 JSON/手工计划操作补齐行为。

现有工作区已经实现过一轮 P1–P6，但 2026-09-20 至 2026-09-21 的真实任务和用户复盘改变了退出口径：P1 不可变版本事实可以保留，P3 的运行服务可复用但入口与反馈必须重做；
需求对话、P2 阶段边界、P4 完成语义、P5 可编辑画布和 P6 正式验收必须按
[R1–R5 修订顺序](REQUIREMENT_DIALOGUE_PREPARATION_AND_REVISION.md#8-实施顺序)重新完成。在新退出条件满足前，不得继续写“产品最小闭环通过”。

### P1 — 运行版本、运行预设与状态投影

交付：

- 定义并持久化不可变可运行版本，固定 requirement、plan、全部 chain reference/digest 和验证证据。
- 定义任务级运行预设，保存默认业务输入与 pacing，并在跨包边界用 Zod 校验。
- 从 job、release、preset、execution 和 archive 事实生成唯一产品状态与主操作。
- 需求修改、修复发布、服务重启和历史数据都不能产生幽灵“可运行”状态。

退出条件：保存/重载后引用与 digest 不变；候选版本不会被直接运行；失效预设不能创建 execution；状态投影有定点合同验证。

### P2 — 准备任务产品编排

交付：

- 已确认需求只有一个“准备任务”主入口，内部执行规划、预执行、编译、样本验证和复用边界验证。
- 准备任务只消费已经清零重要待决项的需求版本；来源解析和用户选择已由需求对话保存，真实页面结构与操作路径由准备阶段调查。
- 将现有 authoring/validation 状态翻译为产品阶段，技术细节进入可展开详情。
- 不再要求正常用户填写预执行 JSON、手工选择 sample/verification 或理解链路冻结条件。
- 来源候选和业务歧义由需求对话解决；预执行确定真实入口和页面路径。现场发现新的业务歧义时暂停并回到需求对话。
- 无法安全得到验证输入时，通过 ValueSchema 业务表单请求一次补充，完成后继续原准备流程。

退出条件：从确认需求到发布运行版本的主路径没有 JSON 输入框和内部验证按钮；准备任务没有替用户决定业务歧义；刷新页面后继续显示同一事实状态。

### P3 — 链路运行台直接运行与参数表单

交付：

- 任务列表只展示产品状态并选择任务；已发布链路在链路运行台支持直接运行/再次运行。
- 直接运行使用当前发布版本和预设，服务端再次校验引用、digest、输入合同和全局浏览器会话所有权。
- 实现有限 ValueSchema 的递归业务表单；支持修改本次输入、保存为默认值和 pacing。
- 防止双击、轮询和网络重试创建重复运行；服务端 accepted 回执返回唯一 execution，运行台立即绑定并显示运行流。
- 列表选择、运行提交、accepted、settled 和 error 都有即时可见反馈；禁止静默点击。

退出条件：用户不进入计划页即可从链路画布运行；无参数任务一次点击创建运行并立即显示 queued；参数失效时只出现表单，不发送运行；列表点击不运行；键盘和触屏可完成同一路径。

### P4 — 结果回执、人工等待与修复入口

交付：

- 按 execution/data `ResultSpec` 分离业务结果和执行回执。
- 发布链路无节点、合同或运行时错误并到达完成终点时即投影为 completed；不得由链外全局语义 judge 改判。
- 完成、部分完成、等待、阻断、失败、取消和 stale 均有明确结果结构与下一步操作。
- 人工等待从结果页恢复同一运行；服务重启后仍可核验现场并继续。
- 可修复失败提供明确模型修复授权，并把失败证据传入新候选生成；外部阻断不显示修复按钮。
- 修复成功后发布新运行版本，旧版本与运行历史保留。
- completed 结果提供独立用户验收意见，并能进入链路修订或带运行摘要回到需求对话。
- runner/browser/temp 清理使用独立状态和恢复入口；清理异常不生成确定性链路修复证据，也不覆盖已完成步骤和业务结果。

退出条件：执行型任务不显示伪造业务 JSON；正常结束不被附加语义 judge 或清理异常改写为链路失败；cleanup_required 可持久恢复且不调用模型；
等待恢复不重复副作用；修复未经用户操作不会启动；新版本通过验证前不替换当前版本。

### P5 — UI 视觉与交互收口

设计方向：延续当前深色、克制、偏工具仪表台的视觉语言，以“任务状态轨道”为记忆点；不进行与闭环无关的全站换肤。

交付：

- 状态颜色、图标、文案和主操作在侧栏、顶部栏、准备页、结果页保持一致。
- 主操作层级明确；技术详情降级到折叠区，不用成排同权按钮暴露内部生命周期。
- 准备和运行阶段提供连续进度、最后更新时间、不可重复派发反馈和错误恢复。
- 参数表单、人工等待和修复确认使用一致的 Dialog/Callout/Field 结构；危险或有模型成本的动作明确说明。
- 链路画布从只读展示升级为直接运行、实时观测和版本化修订的统一入口：节点编辑只写草稿，验证后发布新不可变版本，历史版本只读。
- 优先复用成熟开源工作流编辑器；业务主步骤与完整技术路径在同一张图中嵌套，折叠态可读、展开态可审计，不自研通用画布基础设施。
- 画布只绑定一个明确 execution，以持久化事件展示节点和连线的 queued/running/waiting/succeeded/failed/skipped/cancelled；刷新和重连续接同一次运行，不能混合历史状态或用前端动画伪造。
- 节点详情先展示动作、输入、目标、条件、路由和本次运行摘要，原始 JSON 仅在高级信息中折叠展示。
- 结果页提供“符合预期 / 调整链路 / 重新梳理需求”，并在局部修订与需求回流之间保持清楚边界。
- 完成桌面、窄屏、键盘焦点、可读对比度、空状态、长标题、长错误和 reduced-motion 检查。

退出条件：关键状态不只靠颜色表达；没有 hover-only 主操作；运行点击立即响应；当前真实链折叠态可顺序阅读，展开态无节点重叠、边穿节点或主路径交叉；
用户可以观察一次真实运行流，在不阅读原始 JSON 和内部 ID 的情况下理解主步骤与技术动作，并从该运行进入节点修订或需求回流。

### P6 — 正式产品入口组合验收

只在 P1-P5 完成后执行。验收必须从 Workbench/API 正式入口贯通，不能直接调用 runtime 或临时脚本组装成功结果。

最少覆盖以下独立产品路径；这些是验收路径，不是七种任务类型：

1. **充分需求对话**：同一任务连续解决多个重要歧义，待决未清零时不能确认草稿，用户纠正后旧决定不残留。
2. **来源解析**：无 URL 的唯一候选、多候选 Question Panel 和无可靠候选三条路径均正确；动态目标不冻结为一次性 URL。
3. **准备与执行完成**：自然语言新建 → 确认 → 准备 → 发布 → 重启服务 → 从发布链路画布直接运行；启动立即反馈并绑定唯一 execution，链路无真实错误即 completed，不被结尾语义 judge 改判。
4. **数据与换输入**：业务字段表单 → 同一发布版本不同输入 → 业务结果随输入变化 → 普通复跑模型调用为 0。
5. **人工等待与外部阻断**：登录/验证码同 run 恢复且不重复副作用；频控/访问拒绝不进入修复模型。
6. **确定性失败修复**：真实失败回执 → 用户授权模型修复 → 新候选验证 → 新发布版本；旧版本和原运行保留。
7. **局部链路修订**：从实际运行进入自由画布 → 修改一个节点或受影响连线 → 聚焦验证 → 发布新版本 → 再次运行。
8. **需求回流**：携带运行摘要返回需求对话 → 修订目标或范围 → 确认新需求版本 → 重新准备；画布不偷偷改变需求。
9. **持久化与交互**：重启后任务、版本、预设、历史、修订草稿和待恢复运行一致；真实 Chromium 覆盖列表只选择、画布内启动、即时反馈、运行流刷新续接、桌面、窄屏、键盘、双击保护、错误恢复和最终截图。
10. **清理生命周期与可读画布**：成功链路的 cleanup 正常确认；受控清理异常投影为 execution 级 cleanup_required 并可恢复，不出现节点 repair；exact chain reference 解析唯一不可变 ChainPresentation；当前真实链以阶段总览、单个临时动作摘要和同画布聚焦动作子图呈现，完整路径可审计、节点详情无 JSON 墙。

每个正式运行记录 task/release/plan/chain/run id 与 digest、输入 digest、业务结果或执行回执、browserCommands、modelCalls、
provider reportedInvocations、Browser/runner/QuickJS 清理结果。真实页面用于证明产品可用性，受控页面用于稳定复现等待、失败、修复和恢复；
二者都必须经过同一产品入口。

## 8. 最终交付判定

只有同时满足以下条件，才可以写“产品最小闭环通过”：

- P1-P5 的退出条件全部成立；
- P6 的全部独立产品路径都有真实结果；
- 用户能在任务列表找到并打开已准备任务，再从发布链路画布直接运行并观察本次运行流，不填写 JSON、不操作内部验证按钮；
- 需求对话、准备任务、运行完成、用户验收、节点修订和需求回流各自遵守明确产品语义；
- 没有网站、弹窗文案、CSS class 或业务字段 special case 进入生产源码；
- 普通复跑的模型调用只可能来自显式 LLM 节点；
- 所有 Browser、runner、QuickJS runtime/context 和临时服务都在 `finally` 中释放；
- 未测、基线失败和延期平台边界单独记录，不以“当前机器成功”冒充跨平台结论。
