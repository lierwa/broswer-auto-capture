# 任务方法与完成条件整改：对抗评审

日期：2026-10-07。评审源码基线：`3b8049e`。对象：[整改方案](TASK_METHOD_COMPLETION_PLAN_20261007.md) 初稿。

## 首轮结论

**不准入产品实现。** 初稿正确识别了“动作成功不等于方法可复跑”，并保留了普通复跑零模型、旧版本不可变、普通编译缺口不打断探索等边界；但关键生成机制仍未闭合。将“每步骤一次 boolean”直接实现，会出现漏检、增加语义裁判、只有拒绝而没有处理方法的风险。

本评审只读取方案、架构和相关代码；未运行测试、模型、浏览器或账号任务，未修改产品、AGENTS、主方案或历史数据，未提交 Git。以下行号指首轮方案；后续修订应按小节对应。

## R1 · P1：新门按证据出现与否启用，遗漏本身仍可绕过

- **方案依据：** §4.D 第 105 行称“新准入只作用于采用新方法证据的准备/编译版本”。
- **源码依据：** `natural_selection.py:100-109` 在没有集合读取引用时直接返回空函数、空缺口；`natural_compile_result.py:17-63` 在已有 issues 为空时生成成功图；`hybrid-materializer.ts:43-45` 仅拒绝已有 gaps / not_compilable。
- **反例：** 新任务依然只导航、点击、等待、done，没有产生新判断事实。若以“出现新事实”为启用条件，它继续走旧编译成功路径，原事故原样发生。
- **最小修订：** 明确新 authoring 请求/来源协议的启用版本，不能由可选事实是否存在推断。新版本必须有一次方法结算，分别记录已由现有确定性能力覆盖、已绑定具体局部方法、证据不足。此结算不能由宿主凭关键词或动作数猜业务覆盖。旧来源使用明确旧版本解码/编译；“旧来源可重编译”不能让新来源故意省略字段降级。
- **关闭证据要求：** 给出启用字段由谁创建、缺失/未知版本如何处理、按什么真实语义依据认定覆盖；设计三种输入的预期：新来源缺方法、新来源已有固定目标方法、旧来源离线重编译。仅把“采用新证据”改成“新版本”而不补覆盖判定，不足以关闭。

## R2 · P1：boolean 源码不能同时承担需求分解、读取选择和插入点判定

- **方案依据：** §4.B 第 70-76 行只规定输入步骤全文及实际读取、输出 boolean 源码；§4.C 要把它插在“对应决策位置”，但没有该位置的生产者。
- **源码依据：** `preparation-plan-projection.ts:42-57` 默认可以只有一个 `main` 步骤，内部包含整个业务任务；`selection_annotation.py:26-58` 的现有注解有明确的 action / read 绑定和真实 observedValue；`author_compilation.py:52-72` 也只保存这些动作所属的注解，不拥有任意业务断点。
- **反例：** “先提交 A，再修改 B”被合并到 main。一个终态 boolean 不知道应在提交前还是修改后运行，不能判定必经动作、已保存和仅界面变化，也不能安全决定跳过哪段动作。给所有 main 追加模型生成的总体完成函数，虽不在运行后调用模型，仍重造了总体业务裁判，且超出最小实现。
- **最小修订：** 撤回“每步骤一个完成 boolean”。先限定已有、可明确锚定的方法边界：真实 read → 已观察选择/动作 → 真实后置读取；绑定由该动作及其采集时点决定。选择任务尽量复用原选择函数输出的目标，原生 postcondition 已能表达的状态不增加模型。新的 guard 只能消费可追溯到同一局部动作/方法的状态，不能消费整条轨迹后猜一张新图。没有该锚点时记录缺口。
- **尚未闭合：** 对无动作的业务判断，局部锚点还不存在。方案必须明确如何产生该业务意图和读取引用，不能把“宿主确定”当实现。若确实需要最小语义标记，应说明准确字段及其不可推导性，并评估是否能复用现有原生工具，而不是承诺只返回源码即可拥有全部信息。

## R3 · P1：没有处理动作的成功轨迹，无法凭 boolean 生成可用的未满足路径

- **方案依据：** §4.C 第 90 行只有“保留缺口，准备修复需继续取得方法证据”；§6.2 又要求该初始状态下最终生成可用链并通过未满足场景。
- **源码依据：** `selection_annotation.py:38-51` 的函数例子和目标来自已发生的 action；`natural_selection.py:124-138` 绑定真实 action 的选择值；`AuthorCompilation.finish` 只编译、保存，不继续执行 Agent。架构 §2 / §8 禁止编译缺口自动重开浏览器、自动重放副作用或让模型编写整张图。
- **反例：** 页面一开始已经保存或已经播放，Agent 没有执行处理动作。可以产生一个“当前满足”的判断，却没有如何保存、如何选择并切换的可复跑方法。修改初始状态后只有失败出口，不能完成任务。
- **最小修订：** 将“真实代表处理路径已存在”作为条件分支编译的前置事实；已有路径才能构造有界可选路径，并保留外部写入顺序。对没有路径的情况，必须设计并写清同一次原生探索如何获得方法证据，或者明确由用户发起准备修复取得新来源。不得为让验证通过而自动改坏现场、重复提交、强制点击、关闭再重跑，或把已有写操作当作幂等。
- **关闭证据要求：** 以“初始满足、没有动作”的实际输入走一遍生产者—消费者表，说明控制权、继续探索触发、最多次数、关闭时点和失败出口。当前不存在可不增加信息、凭 boolean 安全补出任意处理路径的方案。若选择仅 fail closed，必须保留“原始事故只防误发，功能未修复”的未完成结论。

## R4 · P1：证据的新鲜度与查询存活，必须在编译顺序上闭合

- **方案依据：** §4.A 只说保留观察时点；§4.D 第 102 行说内部读取不能被裁剪，但没有函数/分支何时接入的顺序。
- **源码依据：** `natural_compile_result.py:20-29` 先 `prune_unused_queries`，再 consumer readiness 和 result derivation；`natural_read_liveness.py:9-25` 只从真实 bindings / target / inputBindings 及有限输出事实找消费者，注解本身不会保住读取；同文件第 127-175 行裁剪后还会重绑定 readiness。`natural_selection.py:36-42` 的示例也证明 URL/tab 相同不能自动代表任意后续状态可复用。
- **反例：** 如果在 materializer 才加 guard，所需读已被裁掉；或者把点击前的“已保存”字段绑定给点击后的确认，两个输出来自同一次运行但时点错误，函数仍可能返回 true。
- **最小修订：** 在 liveness 分析前构造真实消费者绑定；readiness / repeat 折叠之后验证守卫仍支配它负责的出口。读取身份至少要沿既有 document / dispatch 顺序约束，明确哪些读只适用于前置判断、哪些必须在效果完成后重新执行。不能以“本次节点输出”替代时序证明。新读取在 source 关闭前保存，离线编译不得取当前浏览器或重新采样。
- **关闭证据要求：** 补“构造消费关系 → liveness → readiness / repeat → 图接线 → 控制流与时序校验”的具体顺序，并列前后状态相反、同 URL 文档替换、repeat 内外绑定三种反例。

## R5 · P2：版本兼容承诺还缺明确分派；不应扩大到重写旧编译器

- **方案依据：** §4.D 承诺旧来源按原注册表/编译协议恢复，§5 未列实际版本入口。
- **源码依据：** `author.py:305` 固定产生 `bat-hybrid/2`；`hybrid-materializer.ts:48-61,78-86,233-234` 多处以 compilerVersion / context.version 分派。自然来源的 `control` 默认为空，现有自然分支有独立的 resultBranches 物化路径；不是随意增加 Python branch 字典就能复用已有 TS branch。
- **最小修订：** 先定一个窄版本的新增证据合同及确定性分派表，列 producer / Python schema / TS schema / compiler / materializer / digest 全链路。缺省值不能改变旧 canonicalDigest，不要为了这次修复复制整套旧编译器。自然方法分支应复用已有 IR 节点，但有自己受校验的来源适配入口，不能偷偷塞入旧数据结果分支字段。
- **关闭证据要求：** 用精确旧来源和新来源的预期解码路径、摘要行为及未知版本拒绝行为说明兼容；源版本启用与 R1 是同一个决定，不能各写一套。

## R6 · P2：开发夹具的负例不能冒充任意新任务已有独立验收依据

- **方案依据：** §6 的两类受控页面测试明确由开发者给出预期，这一点正确；但 §4 的通用准入没有说明真实任务如何取得 false 样本以及谁拥有期望值。
- **源码依据：** `selection_annotation.py:46-51,97-111` 的现有校验主要证明真实样例输出与已观察动作一致；它不证明该动作满足需求。架构 §10 把用户验收与运行 completed 明确分开。
- **反例：** 模型生成 `return true`，真实现场恰好满足。通过 QuickJS 和原现场复跑不构成负例测试；自动随机改一个字段也不能保证它在业务上应该失败。让同一模型生成自己的预期，会形成自证。
- **最小修订：** 分开记录：编译的结构/证据准入、开发回归对已支持方法的验证、具体新任务的代表执行与变化验收。实际来源无负例时不能伪造，不能宣称所有新任务已保证业务正确。自动变换只能用于明确有数学不变量的任务数据（例如仅调整无业务顺序含义的候选展示顺序），不能默认为任意任务成立。
- **关闭证据要求：** 写清“谁生成输入、谁给期望、验什么不变量、能证明到哪里”；常量 true 的开发回归不得被描述成对所有生产任务的自动检测保证。

## 可接受的最小方向与准入界限

1. **先复用现有 read / selection / postcondition。** 不引入每步骤 completion boolean 服务，不重写 runtime，不扩展 outputSchema=null 的业务输出语义。
2. **窄化到局部方法，先有来源再接线。** 同一明确动作/选择的读取、函数、目标和后态可以通过小适配补齐；没有明确锚点和处理路径时，不能靠命名为“方法判断”而跳过信息缺失。
3. **新增协议需要明确最小信息。** 为消除漏检，版本必须先启用；为准确绑定，来源必须表达真实局部方法意图。这两项不是当前一次 boolean 源码返回能自动解决的。需要在文档中先决定，不能留给写代码时发挥。
4. **原事故须保持双目标。** 阻止没有方法的来源误发布只是防线；得到可复跑的处理方法才是修复。后者未闭合前，不应启动大范围产品修改或拿 B 站账号反复试验。

### 兼容性与新错误检查

- 未发现第二稿新增与已读源码或最高架构明确冲突的承诺。它没有改变 runtime completed、隐式模型边界、只读离线编译、原始动作覆盖或用户必经步骤。
- R5 实施前需再明确“原摘要”具体指**保存的来源摘要**还是要求**重新编译产物逐字相同**。二者不能混为一谈：不得修改历史 source / release；新编译产物若按合法修订生成新 candidate，则应使用自己的摘要及审计，不能复用旧 digest。该措辞属于 R5 未关闭的精确协议设计范围，不新增一套版本机制。
- §4.C 的最终检查可以承接既有 IR / 编译校验；不得据此额外引入通用图分析库或复制调度器。是否缺少必要校验，要在具体新方法合同确定后按最小反例证明。
- 本次撤回不合理设计是必要纠正，不能计算为已修复三个功能。用户所要求的“状态变化后正确执行”仍未获得新的生产者—消费者闭环。

### 更小实现方向的复核

现有 `selection_annotation` 已由具体 action/read 生成源码，`natural_selection` 已绑定其目标，`natural_read_liveness` 已识别真实 inputBindings。对**已经有读取与处理动作**的来源，优先修正具体缺失绑定或后置条件，可能不需要任何新的完成函数或公共字段。

但上述现有能力不能反推出本次 B 站来源中不存在的读取、局部选择意图或切换动作。没有新的精确来源样本前，本 reviewer 不提供“只改几行即可通用解决”的建议，也不把拒绝发布作为完整修复。

上述关闭以收窄后的合同为依据，不是降低原始任务的验收标准：原 B 站仍必须取得运行时选择方法并实际播放才能交付。enum 本身不证明选择语义正确，错误地把 `state_only` 声明为 `recorded` 仍可能存在，必须在具体任务中核对方法与变化行为。

### R7 · P1：未派发导航不能继承“已有成功导航”的证据门

- **具体漏洞：** 第三稿 §5/§6 称复用 function/navigate 和原后置条件，但没有说明未派发方法的 navigate 后置条件来自哪里。`natural_compile.py:104-107` 要求实际 succeeded action 及 pre/post；第 238-251 行要求实际导航匹配及 `natural_postcondition.matched=true`。inspect 没有这些事实，不能装成一次成功 navigate，不能为新功能普遍放松旧证据门。
- **最小补丁：** 在 `/3` 增加独立的 inspected-navigation 来源适配，复用现有 navigate IR 和 `kind=url, bindingArgument=url, settle=NATURAL_SETTLE` 的运行期检查。该条件来源是经过验证的目标方法与能力合同，明确是**等待 sample 验证的效果要求**，不是已有的观察 `matched=true`。来源保留 dispatch=false，不伪造 resultRef / post observation。
- **发布结算：** candidate 可以含这种待验证方法，但 sample 必须实际执行相应 navigation 节点并满足 URL 及后续条件，才能进入发布；不能只看整个 run completed，也不能在 sample 失败后动态改预期或改写原来源。旧 `/2`/真实动作的条件生成原样保留。

### R8 · P1：新增导航换文档，原轨迹的后继不一定还能复用

- **具体漏洞：** 第三稿 §6.5 “保留后续图”范围过宽。探索时 inspect 不导航，之后的 read/click/input 发生在旧文档；复跑插入 navigate 后它们会落到新文档。相同 URL、同一运行或源码中前后相邻，都不能补出缺失的目标文档来源。
- **最小补丁：** 首版无等价真实 navigate 时，将研究插入点限制为尾部：后继只允许 done、纯内部动作，或不依赖旧 DOM/临时目标、运行时重新观察的原生 wait 条件。旧页读取、click/input、第二个方法等后继保持 typed gap，不猜迁移。如果已有同方法真实 navigate，则按原去重规则保留真实路径。
- **B 站可执行路径：** inspect 之后原生 Agent 执行原有 wait，并观察当前正确页面播放状态；`natural_compile.py:257-267` 已支持 page 级 `media_playback=playing` 或 URL 未切换检查。candidate 中为动态 navigate → wait；复跑重新读当前页面 media。inspect 之前的 wait 不能搬到后面，先前 `playing` 值也不能作为导航后的运行输入。
- **范围：** 纯“打开目标”可以 inspect → done，因为 R7 的导航 URL 条件负责实际到达；要求播放则还必须有 inspect 后实际记录的播放等待，不能用导航成功替代播放完成。

### R9 · P2：一次 state_only 提醒不能改变失败/取消收尾

- 第三稿已限定同一 Agent 和原预算，但提示必须仅对 `done.success=true` 且未取消/未受限的 `state_only` 触发。`success=false`、取消、人工等待及访问限制继续原收尾，不能因为新字段再推进 Agent。
- 提示次数放在同一准备请求/Tools 实例，不能在 done 注册函数内部重置。`author_tools.py:use_structured_output_action` 已明确 Agent 构造会再次注册，闭包内重置会破坏最多一次的承诺。
- 这项提醒只针对模型明确声明缺方法，不针对源码生成失败或编译 gaps，不形成函数 repair loop。
