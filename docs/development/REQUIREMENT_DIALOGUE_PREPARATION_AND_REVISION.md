## 1. 核心决定

1. 需求对话负责确认“用户到底要什么、从哪个有依据的来源入口开始试做”，并直接产出唯一的准备计划草案；访谈 Skill 根据完整对话按需联网调查和提问，所有会改变结果、范围、来源、风险或验收预期的重要歧义由用户确认或明确委托。
2. 用户确认草案后，任务准备直接把同一草案交给 B-U 调查真实页面、代表执行、编译和复用验证；内部格式只能投影已确认内容，不得在中间另起一轮模型业务规划或补猜网址。
3. 正式运行的 `completed` 是技术运行结论：发布链路按合法控制流到达完成终点，所有实际执行节点和输出合同均无真实错误。
   不得再附加一个全局语义 judge，因为系统没有额外证明而把已经正常执行的链路判为失败。
4. “运行完成”和“结果符合用户预期”是两件事。运行完成后由用户查看实际结果，并选择接受、调整链路节点，或回到需求对话修订需求。
5. 已发布需求版本和链路版本保持不可变。局部节点调整产生链路修订草稿并发布新版本；整体目标理解错误产生新需求版本并重新准备。

## 3. 产品生命周期

```text
用户描述目标
  -> 需求对话：Skill 按需只读搜索、澄清结果和来源，形成并确认唯一准备计划草案
  -> 准备任务：同一草案交给 B-U 调查真实页面、完成代表执行、生成链路、验证复用边界
  -> 发布不可变运行版本
  -> 正式运行：按图执行；无节点/合同/运行时错误则 completed
  -> 用户查看结果
       ├─ 符合预期：继续直接运行或再次运行
       ├─ 局部链路不对：从当前版本建立修订草稿，修改节点并验证，发布新链路版本
       └─ 整体需求不对：携带运行记录回到需求对话，确认新需求版本后重新准备
```

登录、验证码、一次性授权和访问限制仍是同一运行中的人工等待；它们不是任务类别，也不自动触发模型修复。

## 4. 需求对话的职责

### 4.1 按最终交付选择访谈清单

任务类别只用于选择访谈领域知识，不要求用户先选，也不得成为 runtime 的网站或业务 special case。

| 最终结果类别 | 需求对话至少确认 |
| --- | --- |
| 查询与核实 | 要回答的问题、来源范围、时效、证据和不确定性表达 |
| 数据采集与整理 | 对象、字段、数量、排序、覆盖、终止条件、缺失和不足处理 |
| 文件产物 | 文件内容、格式、范围、命名、有效性和重复文件处理 |
| 状态到达 | 目标对象、期望状态、动态条件和用户如何判断结果 |
| 事务提交 | 提交对象和内容、停止点、不可逆动作、授权和回执预期 |
| 资源变更 | 账号内对象、当前/目标状态、变更范围、可逆性、授权和结果回读 |

多个可独立验收的结果组成混合任务；每个子结果及其依赖都在同一准备计划草案中确认。

### 4.2 待决事项硬门

需求对话维护待决清单。以下内容只要不清楚、存在多个合理解释，或不同答案会改变结果，就必须通过对话或 Question Panel 由用户确认：

- 最终要得到的结果与目标对象；
- 来源、服务、账号范围或内容身份；
- “最新、全部、前 N 条、正片、成功、完成、价格”等动态词和量词；
- 输入中哪些值会在以后复跑时变化；
- 数据字段、文件要求、状态目标、提交停止点和不足处理；
- 不可逆动作、外部副作用和人工授权点；
- 多个子目标之间的顺序与失败处理。

一轮仍只问一个决策轴，但轮次数不设人为上限。只有重要待决项为零，或用户明确授权系统在写明边界下代为决定，才允许生成可确认草稿。

### 4.3 只读来源解析

需求对话可以使用 Pi 当前活动工具集中的受限只读搜索能力补全业务事实，但不能启动任务浏览器、登录、点击、提交或声称已经验证页面操作。访谈 LLM 根据完整对话决定是否需要搜索、何时搜索、搜索词和原始结果与业务含义的相关性；宿主只执行受限工具、清理危险协议、规范化工具返回的引用、校验候选 ID 确实来自本次结果、生成 Question Panel 和持久化用户选择。宿主不得用关键词、通用词表、字符串相似度或分数阈值判断来源语义。

搜索能力不属于模型设置弹窗，也不按 Auth/API Key 或供应商名称分叉。模型设置只选择模型连接；Pi 的 `ResourceLoader`、extension/package 注册表和 active-tools 集合决定本次 AgentSession 实际有哪些搜索工具。分类只看运行时能力来源：可复用已保存凭据的成熟 Pi 搜索 extension、无需额外密钥的通用只读后备、或当前无可用搜索工具。当前模型只决定是否调用可用工具以及如何解释结果。不得给 Claude、Qwen、Doubao 等连接各写一套路由，也不得在模型卡片旁新增搜索状态。

当前固定 Pi 0.84.2 的正式扩展面是 `DefaultResourceLoader`、`pi.registerTool()`、`tools`/`excludeTools` 与 `pi.setActiveTools()`。搜索 extension 与宿主 custom tool 应由 Pi 合并进同一工具注册表；B-A-T 只保留来源证据规范化、稳定结果 ID、安全/预算、候选引用校验和持久化。通用 Bing RSS 可以作为无额外密钥的只读后备，但不是唯一搜索实现，也不拥有语义筛选权。

```text
来源身份或入口仍有结果级歧义
  -> LLM 根据完整对话决定是否搜索及搜索词
  -> Pi 从当前活动工具集中执行模型选择的只读搜索工具
  -> 宿主把真实结果或引用规范化为稳定 ID，不做语义排名
  -> LLM 提交它判断后的真实候选 ID 或无候选结论
  -> 宿主校验引用并生成 Question Panel，用户作最终确认
  -> 无可靠候选或搜索不可用：保持待决，不得猜 URL 或拿无关结果凑数
```

用户确认的是业务来源、可审阅的试做入口及目标对象，不由用户填写 `startUrl` 技术字段。网站名称或别名不是已核验的域名；需要 URL 才能交给 B-U、但本轮没有用户提供或真实搜索引用支持入口时，保持待决并继续调查。动态目标不得被冻结为一次性的结果 URL；例如“最新正片”保存确认来源、入口和运行时选择规则，不预填某一集的内容页。

### 4.4 成稿内容

准备计划草案必须用用户可读语言覆盖：目标、已知上下文、来源身份和引用、可用的试做入口、运行时输入、范围与约束、动态选择规则、结果预期、高层步骤依赖、B-U 现场调查事项、异常与不足、权限和人工确认点。
它不得包含 selector、节点 ID、原始 JSON、E1–E4 或页面控件猜测。

LLM 不生成一份庞大的内部需求 JSON，也不在用户确认后再生成一份可改写业务内容的 TaskPlan。宿主持久化真实搜索引用、模型候选判断、用户决定、待决状态和唯一草案版本；Skill 每轮选择继续提问、受限只读搜索并提交候选，或生成/修订准备计划草案。用户指出草案中的目标、入口或步骤不对时，继续在同一需求对话中修订并重新确认。

### 4.5 如何从普通需求合理拆解到有效草案

访谈从用户要看到的最终结果反推必要条件，不要求用户先写操作步骤。每轮结合**完整对话**维护当前任务理解和待决事实；下表是审阅维度，不是每个任务必须依次回答的问卷，更不是关键词触发的流程图。

| 审阅维度 | 需要弄清的业务含义 | 属于谁的决定或证据 |
| --- | --- | --- |
| 结果与对象 | 最终交付什么；对象身份是否唯一；多个结果是否各自可验收 | 用户原话和纠正优先；对象歧义由用户确认 |
| 来源与入口 | 允许在哪个来源做；入口是否能通向目标集合；为何相信它 | 用户提供的材料或本轮只读搜索；模型判断相关性，宿主校验引用，必要时用户确认 |
| 范围与动态条件 | “最新”“全部”等词在本任务中如何影响选择；对象随运行变化时保存什么规则 | 模型解释备选后由用户决定会改变结果的取舍；不冻结一次搜索命中的内容页 |
| 条件与权限 | 登录、付费、地区、访问权或不可逆动作是否改变可完成对象或风险 | 公开事实可先只读调查；用户自身资格和意愿只能由用户回答；页面当前状态留给 B-U |
| 输入、依赖与不足 | 以后运行哪些值会变化；步骤怎样依赖；无结果、部分结果或阻断时怎样处理 | 结果级选择由用户决定；浏览器控件和定位方式留给 B-U |
| 完成与验收 | 哪些实际状态足以交付；用户如何判断结果符合预期 | 草案写业务完成预期，运行记录提供事实，用户验收另行记录 |

对每个未知，先判断**不同答案是否会改变结果、来源、范围、授权或验收含义**。若不会，就不为展示流程而提问。若公开资料能缩小未知，访谈模型按上下文决定是否只读搜索、调查什么、是否还需用户选择；搜索内容是证据，不等于页面操作或用户决定。若只能在真实页面知道控件、排序、登录现场或播放状态，写成 B-U 现场待查；现场新发现的业务取舍再返回对话。用户明确把某个有边界的取舍委托系统时，记录委托及边界。其余影响结果的选择一次问一个轴，给出可理解的后果，允许自由纠正；询问用户自身事实时不替用户推荐答案。

成稿时只留下**一份可审阅、可确认、版本化的准备计划草案**。草案说明目标与结果、已确认来源和本轮引用、可追溯的试做入口、动态选择规则、运行输入、范围和排除、业务步骤依赖、B-U 代表试做要求、停止与人工确认点、完成和不足处理。搜索记录、Question 与用户决定作为可追溯对话事实保存；草案引用其已确认结论，不把整段搜索输出塞给用户，也不要求用户填写 URL、selector 或 JSON。当前四个固定 Markdown 段名与有限字段类型只是同版技术投影的语法接口，**不决定业务问题、提问次序或网站路径**。

退出条件是重要待决项清零、入口有可追溯引用、用户审阅并确认该草案版本。宿主只校验协议、引用、版本、字段语法和待决状态；不得按网站、词语、内容编号或猜测的会员状态作语义选择。确认后工作台的独立操作才启动 B-U，内部合同只投影同一版本；B-U 自行研究页面怎么操作。当前内部 `TaskPlan` 仍投影为单个 `main` 代表步骤，复杂的多个独立业务结果与依赖尚无本轮正式验收，不能因文档已定义就报通过。

## 5. 任务准备的职责

任务准备只消费当前已确认的准备计划草案版本；B-U 指令可附加同一版本的技术输入和安全边界，但不得增加新的业务步骤或 URL。其职责是：

- 从草案中有依据的入口调查真实页面结构、控件、标签页、登录现场和操作路径；
- 用代表输入真实完成一次任务，记录实际动作、节点输入输出和业务产物；
- 将代表路径编译为参数化 TaskChain，并用同输入和不同输入验证复用边界；
- 处理技术层面的唯一定位、等待、pacing、输入绑定、输出绑定、失败出口和人工等待；
- 把通过验证的草案引用、内部投影、链路版本和 digest 发布为不可变运行版本。

准备阶段可以自行解决不改变业务含义的技术选择。如果现场出现新的来源、范围、停止点、授权或结果含义歧义，必须暂停准备并把一个业务问题送回需求对话；不得让探索模型替用户决定。

准备任务的验证用于证明链路可以按设计执行和复用，不是为正式运行增加一个脱离节点图的全局业务 judge。

## 6. 正式运行完成与用户验收

### 6.1 运行完成

一次正式运行满足以下条件即为 `completed`：

```text
绑定的不可变运行版本有效
AND 图沿合法边到达 completed terminal
AND 所有实际执行节点均返回成功
AND 节点输出和最终业务输出满足已发布合同
AND 没有未处理的人工等待、取消、阻断或运行时错误
```

节点自身的真实检查仍然有效，例如目标无法定位、点击未派发、输入未写入、读取失败、输出不符合合同、浏览器断开或预算耗尽。这些属于真实执行错误。

运行所属 runner、浏览器会话和临时资源的清理结论是独立生命周期事实。链路节点与输出已经完成、但资源清理尚未确认时，TaskRun 的 completed
保持不变，正式 execution 进入 `cleanup_required`，主操作为核验并清理资源；它不是可修复链路失败。若业务执行和清理同时失败，保留原业务主因，
清理作为附加事实。只有资源清理也确认后，正式执行生命周期才闭合为 completed 并允许再次运行。

禁止在链路已经正常结束后，再由来源 judge、完成态 judge 或通用“证明引擎”仅因缺少额外语义证据将本次运行改判为失败。

### 6.2 用户验收

结果页在 completed 后提供三个同级、含义明确的后续动作：

1. **符合预期**：保留当前发布版本，可继续再次运行；确认不是运行完成的前置条件。
2. **调整链路**：打开当前发布版本对应的链路画布并创建修订草稿。
3. **重新梳理需求**：把本次运行的步骤、结果、错误和用户说明带回需求对话，产生新需求版本并重新准备。

运行完成事实和用户验收意见分别保存，不能互相改写历史。

## 7. 自由画布与链路修订

链路画布是正式产品的链路运行台，不是只读技术详情。它至少支持：

- 在当前发布版本上直接“运行/再次运行”；预设失效时从同一位置打开业务字段表单，不要求 URL、selector 或 JSON；
- 点击后立即显示 submitting/accepted/error，accepted 后绑定唯一 execution，并按持久化事件展示节点和连线的实时运行流；
- 左侧任务/session 列表只选择任务并提供即时选中/加载反馈，不启动运行；
- 展示当前发布版本、历史版本、输入输出、本次运行记录和错误；历史运行通过明确选择器切换，不混合状态；
- 同一 TaskChain 以阶段总览、单个临时动作摘要和同画布聚焦子图呈现：总览能读懂任务顺序，进入阶段后查看实际动作节点、分支和异常出口；
- 从当前发布版本创建可编辑修订草稿，不直接修改已发布版本；
- 修改单个节点的业务可读参数、目标描述、输入绑定、输出绑定、失败路径和连线；
- 对节点或受影响下游执行聚焦验证；上游输入或现场无法安全重建时，明确要求从更早节点或整链验证；
- 验证通过后发布新不可变链路版本，并更新任务的可运行版本；旧版本和历史运行继续可读；
- 用户主动请求模型辅助修复时，显示模型成本和真实失败/运行证据；普通手动编辑不隐式调用模型。

局部修订不得改变已确认需求的业务含义。若用户要修改目标、来源、范围、结果或风险边界，画布必须引导回需求对话。

画布的节点、连线、端口、选择、重连、视口和缩略图继续复用现有 React Flow；阶段总览和聚焦动作子图的初始有向布局复用 Dagre。B-A-T 只实现 TaskChain、链路阶段、不可变 revision、运行事件、capability descriptor 和产品命令的薄适配，不重写编辑器或布局算法。FlowGram/Coze 保留为交互参考，不引入其大容器子画布和广泛状态所有权。

`apps/workbench/prototype.html` 只固定已经确认的交互层级，不是产品事实源。生产实现必须先完成[正式复跑恢复与链路工作台开发基准](EXECUTION_LIFECYCLE_AND_CHAIN_WORKBENCH_ITERATION.md)的 I1–I4 服务端合同，再按 I5–I6 接 UI 和发布；不得把原型静态数据、模拟运行状态或样例任务文本复制到生产路径。

## 8. 实施顺序

### R1 — 需求对话与来源解析

- 重写项目内 `interview-browser-task` Skill；增加待决清单硬门和结果类别访谈清单。
- 恢复 Pi 的 ResourceLoader/extension/tool 注册边界，使成熟搜索 extension 与通用只读后备通过同一 active-tools 机制进入访谈；模型决定是否搜索、搜索词、调用哪个可用工具和候选语义，宿主只规范化证据并校验结果 ID，候选经过公共 Question Panel 后保存用户选择事实。
- 模型设置不展示或配置搜索；Auth/API Key 仅是模型连接凭据。不得在 B-A-T 业务代码中维护按供应商名称分派的搜索矩阵。
- 修改访谈提示词，取消 execution/data 二分，不按关键词或网站分类。
- 确认需求时保存真实来源决定和具体完成预期，不能继续生成开放 input/output 加通用 completionCriteria 的空壳。

退出条件：无 URL、唯一候选、多候选、无可靠候选、动态词和用户纠正均从正式 Workbench 对话入口通过；重要待决项未清零时不能确认草稿。

### R2 — 准备边界与运行完成语义

- 准备任务只研究页面实现；发现业务歧义回到需求对话。
- 删除会在链路正常执行后把结果改判为失败的全局语义 judge/来源 judge；保留真实节点、合同和运行时错误。
- browser-use 代表执行关闭 `use_judge`；新来源 trace 不保存 `judged` 结论，旧 v1 trace 只读兼容且其 judge 字段不再是门。
- 需求、步骤和计划中的完成预期仍供访谈、准备、画布与审阅使用，但 chain/step/plan 结尾 predicate 不得在合法终点之后再次改判运行；完成证据记录实际 terminal。
- 编译缺口明确标为 `confirm_intent` 时，准备任务持久化需求回流事实并引导用户回到需求对话，不能原样重试或让探索模型决定。
- 结果投影明确区分 completed、waiting、blocked、failed、cancelled 与用户验收意见；内部错误码只留在技术详情。

退出条件：一个已在浏览器中完成动作且所有节点成功的正式链路稳定保留 TaskRun completed；资源清理未确认时进入 cleanup_required 而不是链路修复，
清理确认后 execution completed；真实节点错误仍准确失败，不以隐藏验证或清理错误替代主因。

### R3 — 可编辑链路画布

- 先建立运行命令 accepted execution、事件序列和单次运行查询合同，再接链路运行台；UI 不得用本地动画伪造运行事实。
- 保留 `@xyflow/react@12.11.6`，以 `@dagrejs/dagre@3.1.1` 分别布局阶段总览和聚焦动作子图；不引入 FlowGram 或 ELK，不自研通用画布与布局能力。
- I4 先建立服务端 ChainPresentation、链路阶段、CapabilityDescriptor、revision checksum/digest 和验证失效合同；I5 再接阶段总览、单个临时动作摘要、同画布聚焦、直接运行和实时节点/连线流；I6 最后接上下文编辑、浏览器目标选择、聚焦验证和发布。
- 服务端负责不可变版本、权限、校验和 digest；UI 不直接覆盖发布链。

退出条件：用户可在版本化画布直接启动复跑并观察这一次 execution 的真实运行流；阶段总览可顺序理解任务，单击只出现一个临时动作摘要，进入阶段后真实动作子图不重叠、主路径不交叉且可审计，节点详情无需阅读原始 JSON；
修改并验证后发布新版本，旧版本和历史运行不变。

### R4 — 结果复盘与需求回流

- 结果页提供“符合预期 / 调整链路 / 重新梳理需求”。
- 回到需求对话时附带可读运行摘要和用户指出的问题，不暴露原始技术合同；确认新需求后重新准备。

退出条件：局部问题不必重做需求访谈；整体理解错误不在画布里偷偷改变需求。

### R5 — 正式产品验收

只从 Workbench/API 正式入口验证需求对话、来源解析、准备、画布内启动、实时运行流、资源清理、用户验收、节点修订和需求回流。不得用 mock、fixture、runtime 直调、
类型检查或临时脚本代替产品闭环。2026-09-21 第三次真实复跑使本门重新打开；只有新迭代的清理恢复、可读画布和正式再次运行全部通过后才能恢复完成结论。

## 9. 合格线

- 需求对话不会因为已经问过一两个问题就结束；所有影响结果的重要歧义都有用户决定或明确委托。
- 用户不填写 URL、selector 或 JSON；来源歧义由搜索候选和 Question Panel 解决。
- 需求确认事实足够让准备任务执行，不再由准备模型猜业务来源和完成含义。
- 任务准备只负责真实网页实现，并能把新业务歧义送回对话。
- 正式运行无真实执行错误即 completed；用户不满意不篡改运行事实。
- 用户能从发布链路画布直接运行并立即看到反馈和本次运行流；左侧列表只选择任务。
- 用户能在阶段总览理解任务、在同一画布聚焦真实动作子图、修改单个节点并经聚焦验证发布新版本，也能携带运行记录返回需求对话重新准备。
- 普通复跑仍不调用模型，显式 LLM 节点除外；人工登录和验证码继续同 run 恢复。
- 生产源码不加入网站、业务字段、页面文案或 CSS class special case。
- Windows x64 必须从真实产品入口重新验收；macOS arm64 继续记录为用户延期、未测。
