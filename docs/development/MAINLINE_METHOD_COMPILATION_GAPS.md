## 1. 主线只做什么

`确认需求 → 探索现场方法 → 保存一份来源 → 离线编译 → 样本与独立复验 → 手动发布 → 正式运行与交付`

探索现场方法包括：从哪里进入、如何定位记录及字段、如何操作、何时继续或停止、结果从哪个读取产生。代表数据只用于核验这些方法。集合的全部业务数据由生成的链路在运行时取得；预执行不承担先取完业务全集再交给模型转写的职责。

来源事实和正式业务完成必须分开：证明一段代表方法可执行，不等于完成全部业务任务。当前 `done` 已改为只交 `success/reason/readRefs`，宿主从已验证读取装配代表输出。读取仍复用既有 `ReadSpec/read_fields`；最终输出合同不因采样而改写。此变更已有局部编译证据，尚无真实产品任务验收。

## 3. 先锁死的交接原则

1. **方法只有一份。** 复用现有 `ReadSpec` 和浏览器能力；记录容器、相对字段定位、属性/文本投影描述运行规则。字段类型来自确认后的数据合同，不在多个模型响应中独立定义。
2. **样本带覆盖范围。** 样本、页面/document 身份、方法摘要和动作引用证明某次方法核验；完整性与稳定性由宿主记录，不能由模型自报。不能为让少量样本通过而放宽正式结果数量约束。
3. **值由读取产生。** 完成输出引用真实读取或既有变量，宿主装配当前值；不再要求模型抄整页条目，也不能通过修改真实 URL 来满足模型输出。
4. **控制只有一套。** 重复体、继续条件、累积绑定和有限预算进入已有 source/编译链，再物化成现有 Chain IR。done 只交引用，不新增另一套循环脚本语言、浏览器脚本执行器或模型业务计划。
5. **继续条件是动态事实。** 每轮重新读取；不能把本次 `true`、已观察页数或样本条数固化成业务停止条件。来源键去重只处理重复结果，不把重复页当作已遍历完成。
6. **最后一轮必须计入结果。** 最后一页同样回到 loop 累积，然后依据条件结束；limit、阻断和读取失败各保留失败/等待事实。
7. **编译错误留在编译层。** 缺证据返回 gap，来源保留；不自动重新探索，不把不合法候选段包装成跨语言 schema 错误。

## 4. 实施顺序与退出门

### A. 先闭合单次读取方法

将当前 `extract → 最终值倒推 DOM` 的主线改成 `受限读取方法 → 现场代表核验 → 真实读取引用 → read-fields/ValueBinding`。先核验现有原生查询、ReadSpec 和公开 Tools 注册接口能直接复用的部分；旧逐条 DOM refs 工具不能原样恢复。采样与运行方法分离，与输出合同的类型/数量检查在正确阶段执行。

前轮最小所属验证：采样 13 项、方法工具 7 项、方法证据 8 项、引用完成 4 项、done 边界 6 项、完整自然编译 2 项；TS 方法来源 11 项和 API 类型检查通过。但第 6 节随后证明其中存在错误预期与入口覆盖不足，故不能据此关闭 A 门。本轮纠正后的证据见第 7 节。数值祖先路径不能安全放宽时仍严格拒绝，不假称支持所有嵌套采样。

### B. 再接通重复控制

在 A 的真实读取和方法引用上连接循环体、每轮重新读取的继续条件、累积结果与预算，复用现有 LangGraph/TaskChainRuntime。不从重复的动作名称推断循环，也不要求完整抓取所有页才知道如何循环。

最小所属验证：同一方法在不同数据量上复用；一页、两页与更多页的最后一页均计入；重复来源键去重；退出条件变化；预算耗尽为 limit；失败/等待不冒充完成；零隐式模型调用。此门当前**未实现/未通过**。

### C. 能力门通过后再跑产品任务

A/B 的来源、编译、执行边界通过所属最小验证之后，才从正式工作台创建新的普通需求。分别记录首次 B-U、首编译、样本、独立复验、手动发布、正式复跑、UI/API/SQLite 和可见原窗口交付。失败留在原阶段处理；不以旧任务、旧 Release、开发脚本改稿、同版第二次成功补称首次通过。

本轮没有启动新的 B-U 或正式产品任务；局部方法验证不能计作 B/C 通过。

## 6. 配套方法的架构职责与正确性复审

本节记录修复前的只读审查；当次未运行测试、产品任务、浏览器或修改生产代码。后续修复见第 7 节，原有改动全部保留。

### 6.1 应保持的系统分工

| 层 | 它必须证明什么 | 不应由它承担什么 |
| --- | --- | --- |
| 已确认草案 | 目标、来源、范围、业务选择与最终结果含义 | DOM 选择器和另一份模型业务计划。 |
| 原生 action 与 A 采集 | 动作是否实际派发、实际目标/事件、相关前后现场 | 用工具成功回执代替实际效果或业务完成。 |
| B 定位/读取 | 临时索引转可重新解析目标；字段归属、记录范围、读取身份一致 | 把样本数量或技术上限解释成业务选择。 |
| C 动作准备/等待 | 正确现场上的单次派发；后态就绪后再推进 | 重试等待时重新点击、提交或翻页。 |
| 编译与 ResultBinding | 把已证明方法、依赖和控制映射成可满足结果合同的链 | 把代表样本的宽松准入用于正式值绑定，或从重复动作名称猜循环。 |
| LangGraph / TaskChainRuntime | 执行已有节点、动态条件、累积、预算、恢复与审计 | 再探索路线、隐式调用模型或重新理解业务目标。 |

既有 `TargetResolver` 的重新定位/唯一性、`OrdinaryCapability.execute_checked` 的单次派发、`StepVerifier` 的后态轮询是必要的正确职责。源码将派发放在轮询之外；既有动作计数测试保护该不变量，本轮未重跑。不能因配套函数较多而删除这些职责。

`bat_scroll_to` 与 click/input 的自动滚入视野有职责重叠；`bat_wait_for` 与目标准备及 ConsumerReadiness 也有重叠。只有独立的滚动/等待需求无法用当前链表示时，才判断是否开放显式工具。上一轮“未注册所以补入口”的推断不足。

### 6.2 已证问题

1. **P1，准备兼容性越界到正式结果。** `method_read_schema.py:20` 与 `hybrid-method-evidence.ts:29` 忽略数组 min/max，`hybrid-result.ts:147/187` 将其用于正式 ResultBinding/assembly。单次读取 maxItems=300 可以直绑最终 minItems=1000；没有累积节点，值域却互斥。`test_method_completion.py` 曾把这种装配无 gap 当成预期。完整编译测试则移除了最终数量约束，没有覆盖这个矛盾。准备接受少量样本合理，但编译必须拒绝静态不可满足的绑定。
2. **P1，业务选择、读取预算和基数约束仍有混用。** `method_read_tool.py:60-69` 把最终数组约束改成每次预算且强制 requireComplete。已确认取前 10、当前 DOM 100 条时，采样可结束而正式读出 100 条，缺少选择操作导致最终合同拒绝；把预算降到 10 又会在采样完整性检查处拒绝。旧 `read.py` 注释以 maxItems 截取前缀，B 设计文档却规定数量上限不能隐藏截断。应先统一业务选择的所有权，不能把恢复旧 slice 当成正确修复。
3. **P1，标量数组不遵守同一采样范围。** 既有 `_read_shape` 把字符串数组包装成一个容器中的多值字段；新采样只限制容器数。一个容器的 100 个标题仍全部读取，coverage.sampled=1。复用字段投影正确，不代表采样适配已正确覆盖所有输出形状。
4. **P2，派生值仍把样本当完整业务结果。** `method_completion.py:49` 从样本计算 count=3，代表 schema 只删除数组 minItems；若最终 count.minimum=1000，合法方法仍无法完成准备。不能用继续放宽所有业务约束解决；需以现有读取证据和派生关系表达准备事实。
5. **P2，空查询只修了消费者。** `find_elements_read_spec` 已允许完整空查询，但真实生产者 `dom_evidence.py:206` 仍要求 total>0 才 complete；`capture.py:206` 因 complete=false 跳过读取事实。新测试构造 complete=true 的空查询，不能证明真实采集入口已接通。应从原生结果生产者贯穿验证，字段方法的零样本仍不能冒充已获证明。

多步/each 的代表值传递也未闭合：`authoring-progression.resolve` 对代表结果按完整输入合同校验；each 增加数字路径后，代表 schema helper 拒绝数字路径。当前新需求投影仅 main/once，因此此项是公共能力限制，不是所有当前新任务必败的原因。

### 6.3 待证风险与已排除假缺陷

- 探索 click 走原生 Tools，正式 click 走经过目标准备的物理 CDP 输入。正式拒绝遮挡可能正确；已有干扰夹具不能证明当前生产编译有故障。需要依据已有 `NativeEventCapture` 的 isTrusted、目标与文档事实限定支持范围，并由正式 sample 验证，不新增事件协议。
- 正式 read_fields 的单次逐记录投影与准备阶段双读/文档身份核验强度不同；现有后态等待也不能自动证明后续所有读取原子一致。没有本轮复现，列为读取一致性审查项，不宣称是旧错误根因。
- 动态 ordinal 在 TS materializer/runtime 已物化后才交 Python；不存在仅凭 Python 预解析顺序推断出的主入口漏绑定问题。

### 6.4 修复顺序的决定

先修正代表证据与正式结果的界线、统一读取/选择/数量职责，并用真实生产者到消费者的最小证据检查；据此复审本轮新增 method 适配是否能合并回既有边界。之后才补尚缺的重复方法证据与编译，直接复用既有 loop/predicate/accumulator。普通单步任务不应被强加循环；重复任务也不能靠把 loops 从空改成有值完成。以上正确性门通过前，继续禁止新产品任务验收。

用户复核指出：100 条只是说明方法提炼的例子，不能将此例子当成需求，围绕它增加测试后声称系统能力进展。本轮并未创建可由真实浏览器访问的测试页面；模拟 DOM/CDP 和 Node 执行投影脚本只保护局部程序不变量。停止追加此类数量夹具，先完成方法、依赖和重复控制从现场来源到现有 IR 的设计与接入；真实浏览器行为、方法复用和产品闭环目前均无本轮证据。

**仍未通过的门：** 前 N/其他业务选择要有真实选择操作，当前修复只阻止缺操作的链被误编译；自然重复体、动态继续条件和累积的编译仍缺失；多步/each 的代表值传递未闭合。修这些能力前不进入新产品任务。正式 UI/API/SQLite、首次 B-U、首编译、样本、独立复验、发布、正式复跑和原窗口交付均未由本轮局部验证覆盖。

## 8. 基础设施正确性、充分性与 LLM 字段所有权审查

本节为用户重新明确推进方式后的只读审查。未修改生产代码，未运行测试，未创建测试页面、浏览器或产品任务。依据当前源码，不以函数存在、旧测试数量或旧任务成功认定整段可靠。

### 8.1 稳定的具体含义

- 对相同版本、相同输入、相同已记录来源，解析、投影、编译和数据处理给出可解释的同一结果或明确错误。
- 每次实际调用有独立身份；恢复只能复用该次调用、该输入、该版本的已完成事实。
- 页面会变化。浏览器适配必须核验需要的现场条件；不满足时停止或按已有规则等待，不能静默换目标、混用输入或因等待而重派副作用。
- 接收、保存、校验、编译、验证、发布、执行各有明确产物；失败留在所属阶段，上一份有效事实不被不完整候选覆盖。
- 模型只负责语义判断、业务选择和现场方法。版本、摘要、来源身份、工具执行事实、值装配与状态推进由宿主承担。

### 8.3 确定问题及最小所属修复

**F1，子链输出跨调用误复用。** `packages/runtime/src/task-chain/runtime.ts:423–429` 先按 `chain.id + stableKey + completed` 找旧输出，随后才计算当前 invocationId/childInput。合法链允许两个不同 invoke 节点调用同一子链；once 的 stableKey 同为 once，第二个节点会跳过本次执行而复用前一节点输出。本次输入、子链 version/digest 均未比较。外层 loop 重入时 invocationId 也没有包含已有循环现场。

既有 `invocationProgress` 已有 invocationId、完整 chain 引用和 inputDigest；父 idempotencyKey 已含执行现场。最小修复是在解析本次输入后，以完整调用身份定位记录，再核验版本及输入摘要。复用现有字段，失配在派发前明确失败，不新增一套缓存或恢复协议。这是本轮最高优先的确定性运行基础问题。

**F2，缺失业务字段被默认成另一种语义。** `interview/protocol.ts:246` 要求数据结果明确结果形状；`preparation-draft.ts:66–82` 却允许 shapeLines 为空，然后以 `recordList=false` 生成单条记录。缺失时应返回具体不满足项，保留上一有效状态，不能替模型决定用户要单条还是列表。修正准入条件即可，无须再造一份计划。

**F3，选择注解要求拒绝，却没有合法拒绝响应。** `selection_annotation.py:152–170` 要求证据不足时 refuse；`SelectionProgram:21–34` 只允许 source 和 examples。模型无法通过同一合同表达缺证，异常被汇总成 annotation_unavailable。应在原有注解结果边界表达方法可构造或证据不足，并保留具体 gap；服务不可用与无法根据证据生成方法应可区分。没有理由因此加第二个 Agent loop。

**F4，发布结果与请求回执不在同一事务。** API 入口 `app.ts:177–184` 直接调用 service.dispatch；`service.ts:259–267` 先调用 product.publishDraft，再写 recordOperation。`product.ts:28–49` 的事务只包含 Release 保存与活动草稿删除。若后续请求记录写入失败或进程在两者之间退出，Release 已生成、草稿已删除，但请求没有完成回执；相同 requestId 重试会找不到原草稿。应将本地发布事实与请求幂等记录置于同一现有 SQLite 事务。此处不涉及 LLM，也不需要新增状态机。本轮为源码确定的故障窗口，未进行故障注入。

**F5，来源提案重复声明结果数量，且两种搜索引用不能混同。** `source-resolution.ts:20–26` 的 proposal 要模型写 searchTool/subject/query/outcome/candidateUrls；outcome 由选中的 0/1/2 个 URL 已能确定，可由宿主派生。后备 search_sources 把 searchId/results.id 返回模型，具备精确引用条件；原生 Pi web_search 只被宿主旁听，宿主生成的 candidateId 没有回写原工具结果。因此目前不能把两个入口直接统一改成模型提交 ID。后备按 query+subject 找最后一次搜索还存在重复查询不能精确引用旧结果的问题。先做已证可行的减法；若统一引用，须通过现有公开工具适配面让模型确实看到引用。

### 8.4 模型字段与宿主字段分开计数

AuthorInput 的跨语言字段、source/v3 的 canonicalRequest、内部版本/摘要不属于模型输出负担。删除它们不能证明降低 LLM 不稳定性；需要减少的是模型重复生成事实、猜缺项及复制完整宿主结构的责任。

### 8.5 从此处逐段推进

1. **先锁定非 LLM 调用和持久化身份。** 修 F1、F4；要求同一真实执行器对不同调用/输入不混用结果，恢复只继续原调用；SQLite 发布和请求回执同成同败。复用原运行器、字段及事务。
2. **再锁定模型结果准入和拒绝。** 修 F2、F3；确认失败候选不推进，不让缺项变默认语义。现有访谈失败保留与 source 原文保存继续复用。
3. **按真实可见接口减字段。** 处理 F5 和读取工具响应中的内部证明；保留程序内部必需证据。每个删除项要说明宿主能从哪份唯一事实推导，不能仅数外层字段。
4. **再判断能力是否足够。** 将真实入口能产生的任务数据、来源能记录的方法、编译能构造的 IR 与运行器能力逐项对齐；缺生产者/消费者的能力不能靠手造复杂合同补测试来宣称接通。重复方法编译在此后处理。
5. **验证必须针对该层的真实职责。** 纯解析/图运行用真实解析器和运行器；事务用隔离数据库及故障边界；浏览器定位/派发/等待/读取用真实浏览器受控现场。模拟 DOM 只保护局部函数，不能替代浏览器证据。各层有证据后，再从正式工作台做一条全新普通需求的逐门验收。
