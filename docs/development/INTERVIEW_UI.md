# 需求对话：机制、层级与实现边界

更新：2026-09-12。范围：持续需求对话、多任务归属及其向通用任务链路的版本化交接。工作台信息层级见 [工作台布局](WORKBENCH_LAYOUT.md)，完整运行阶段见 [产品流程](PRODUCT_FLOW.md)。

## 1. 产品边界

需求访谈帮助用户把自然语言目标整理成可审阅的目标、输入、约束、完成标准、现场调查事项和权限边界。访谈不搜索网页、不控制浏览器、不设计选择器，也不产生执行授权。

数据采集、信息核实、媒体控制、事务办理和站内管理都使用同一份完整 Markdown 需求。任务类别只帮助选择领域知识，不进入公共合同或运行时分支。网站、业务实体、字段和数量只属于当前需求及后续计划的动态数据。

## 2. 信息层级

| 信息 | 主界面保留什么 | 二级内容 | 原因 |
| --- | --- | --- | --- |
| 对话 | 按到达顺序的用户原文、助手回复、当前问题及建议 | 完整历史通过滚动回看 | 对话上下文是当前任务本身 |
| 草稿 | 消息中的文档卡、当前版本入口、确认状态 | 完整 Markdown、版本选择和确认按钮 | 长文档需要专门阅读，同时保留入口和状态 |
| 决策 | 当前必要问题；2–3 个有真实后果差异的方向及同面板补充 | 历史问题在对应消息只读保留 | 选择与补充都必须绑定 Question identity/revision |
| 计划 | 计划版本、步骤、依赖、动态输入输出合同、预算和验证状态 | 代表输入、链路版本绑定和验证记录 | 计划说明做哪些步骤，不混入浏览器临时现场 |
| 链路 | 独立画布、步骤切换、节点/分支/循环和验证状态 | 节点参数、规则、完成条件和运行说明 | 链路是一个步骤的参数化执行方式 |
| 结果 | 完成/部分完成、结果、关键缺口和总消耗 | 来源关联、检查点、运行与模型审计 | 有实际运行结果才能判断完成 |

## 3. 当前访谈机制

访谈按用户最终要得到的结果选择领域知识，不要求用户先选类别。每轮只处理当前最影响结果的业务取舍；页面入口、结构、字段可得性和访问状态属于后续现场事实，不转嫁给用户。

问题通过 AI Connect 公共 Authoring/Question 协议生成。互斥方向使用 `choice`，同一决策轴内可并存的条件使用 `multi_choice`；每题有 2–3 个真实方向、一个推荐项和同面板自由补充。Composer 始终允许自然补充、纠正或拒绝。历史问题锁定，答复绑定当前 Question identity 和 revision。

成稿只使用宿主私有 `interview-markdown` Flat XML 指令：标题在属性中，完整 Markdown 直接放在正文中。新记录不生成结构化 brief 或 `interview-result`；数据库里的旧 `brief` 字段只为原样读取历史草稿而保留，不能再次成为执行合同。

可靠问题或完整草稿本身可以构成一轮成功结果。问题和草稿互斥；没有安全正文、问题或草稿的输出失败。模型建议不能替代关键用户事实。最新明确纠正重写整份草稿，不能残留旧对象、旧数量或被拒绝的边界。

AI Connect React 公共 Agent surface 负责 Timeline、生命周期、Composer、模型设置、Question 注册与答复、停止和重试。ProductStore 中校验后的消息、问题、草稿、决策和确认是业务事实源；模型事件用于生命周期与审计，不能成为第二份正文事实。

每轮冻结已经保存的账号、模型和 effort，并通过 Pi AgentSession 执行。访谈只注入项目私有 Skill；全局 Skills、MCP、shell 和本机 AGENTS 不参与该模型会话。失败或取消保留已提交对话，重试最近一次用户输入时不重复追加原文。

## 4. 确认与任务链路交接

需求确认绑定 `taskId`、草稿版本和 revision。任意新输入立即使当前确认失效；确认动作不调用模型，也不产生浏览器授权。

确认后的 Markdown 转成版本化 `TaskRequirement`。需求、计划、链路和运行分别保存自己的版本事实，并通过引用与 digest 锁定：

1. 规划器从已确认需求形成步骤、依赖、动态输入输出合同、预算和完成条件；规划阶段不打开浏览器。
2. 来源发现、字段核实或其他现场调查按任务需要成为普通计划步骤，不另设只服务数据采集的固定 Research 阶段。
3. 用户为每个步骤提供代表输入并单独启动受控探索；模型依据 fresh observation 找到代表路径，随后编译候选链路。
4. 候选链路先 sample，再用不同输入 verification。两次运行都受版本、来源域和预算约束；临时元素引用不得进入持久链路。
5. 全部链路 verified 后，用户再冻结计划版本、总预算和正式执行授权。普通复跑由唯一 runtime 执行，只有显式 `llm` 节点可以调用模型。
6. 登录、验证码或人工确认使用 typed `human` 等待点；恢复同一运行前重新观察浏览器状态。页面漂移或预算耗尽会保留进度并阻断，不会让模型逐项接管。

## 5. 持久化与验收边界

SQLite/Drizzle 保存任务、消息、轮次、Question 答复、草稿版本、确认、通用计划、链路、授权、运行、检查点、消耗和审计。旧 JSON 与旧 SQLite 行不做破坏性迁移；新 API 不再写旧 plan/chain/capture 事实。

当前验证覆盖公共访谈协议、确认交接、通用合同、唯一 runtime、BrowserSkill adapter、持久预算与 Workbench 投影；预先明确步骤的公开页面链路已完成真实浏览器运行和复跑。它不证明简短自然语言经过访谈后能可靠形成计划与链路；第二类非数据采集任务和真实登录/人工返回仍需现场验收。
