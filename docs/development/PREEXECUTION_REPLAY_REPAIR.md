# 预执行、复跑验证与访问频控修复说明

日期：2026-09-14
状态：实施基准

## 1. 目标链路

```text
已确认需求
  -> 生成版本化 TaskPlan，划定少量可复用步骤及 once/each/batch 依赖
  -> Pi AgentSession + BrowserSkill 依次探索每个步骤的一条代表路径
  -> 保存各步骤真实业务结果、工具轨迹、字段来源和访问事实
  -> 为每个步骤生成一条候选 TaskChain
  -> 正式运行器复跑验证
  -> 失败分类
       -> 本地链路或编译错误：复用预执行证据修复，生成新链路版本，再验证
       -> 模型质量错误：继续同一探索会话；仍失败时升级可用模型
       -> 登录、验证码、频控或站点拒绝：保存现场并暂停，不自动重试
  -> 代表输入和不同输入都通过后冻结链路
  -> 用户授权正式运行
```

代表探索的完成标准是：Pi 在真实浏览器中完成计划内每个步骤的一条真实调用，并分别提交符合步骤输出合同的业务结果。`once` 完成一次完整调用；`each` 只探索集合中的第一个代表输入，剩余输入由普通执行器逐项复跑同一链路；`batch` 把完整集合交给一条带 `loop` 的链，代表探索仍只处理第一项。发现步骤只收集后续调用所需的可见目标，不能为下游字段提前逐项进入详情。它不执行需求访谈协议，也不以工具事件数量决定节点数量。

## 2. 当前不足

| 当前行为 | 问题 | 修复要求 |
| --- | --- | --- |
| Pi 先完成整项任务，再从执行记录派生一个计划 | 一次探索会逐项处理完整集合，模型不稳定会放大为长链，最后只能得到执行回放 | 计划先划定可复用边界；发现步骤取集合，逐项步骤只探索一个代表输入 |
| 探索只调用一次 Pi；漏交业务结果后直接 `exploration_business_result_missing` | 模型结束回答等于任务终止，真实浏览器现场和已取得轨迹没有得到继续利用 | 在同一 AgentSession 和 BrowserSkill 会话中提供缺口反馈并继续；限定次数后才升级模型 |
| 计划、探索和编译使用同一模型选择 | 低质量模型会同时影响任务理解、工具执行和编译注解 | 按用途路由；探索质量失败可选择同账号中更强且支持 AgentSession 的模型，并记录审计 |
| 验证失败只把候选保持为 `candidate` | 没有“修复—验证”闭环，预执行成功也不能保证沉淀链路可运行 | 新增有界修复循环；每次修复生成不可变的新版本，并绑定失败运行和原探索证据 |
| 访问控制只在收到 `rate_limited` 等错误后熔断当前内存会话 | 多次探索、样本验证、换输入验证会连续访问同一来源；服务重启后压力事实丢失 | 增加持久化、按站点范围计量的主动访问门；控制随机间隔、滑动窗口、递增延迟、人工验证后冷却和单并发 |
| 不同验证阶段可以由用户连续触发 | 即使每次运行合法，组合起来仍可能超过站点容忍频率 | 所有探索、验证、修复验证和正式复跑共用同一站点访问账本 |

## 3. 模块边界

### 3.1 运行指导文档

运行指导文档沿用已确认 `TaskRequirement.definition` 的版本、摘要和确认事实。预执行只读取：

- 目标、范围、约束、代表输入和可观察完成标准；
- 允许访问的公开来源与动作范围；
- 输出合同；
- 登录、验证码、发布、支付等必须交还用户的边界。

平台不把访谈 Question/XML 投影传给预执行，也不把某次搜索结果或临时元素引用保存成下次复跑依据。

### 3.2 计划

计划只描述用户每次正式运行都要发生的业务步骤。纯本地汇总、链路验证、修复和产品生命周期不得成为计划步骤。上一步输出集合、下一步各项互不影响时使用 `each`；需要跨项累计、去重或按真实结果停止时使用 `batch`，整份集合传入一条带显式 `loop` 的链。

计划生成必须直接接受本次代表输入，保留字段名和基础类型，不得把样本值冻结为枚举或相同上下界。步骤合同只展开跨步骤绑定、完成判断和最终结果必需的结构，避免把整份需求说明复制为深层 schema。

### 3.3 代表探索

一次任务 authoring 只拥有一次 Pi AgentSession 与一次 BrowserSkill 会话。Pi 按计划依次完成各步骤代表调用。宿主负责：

- 工具授权、轨迹、业务结果与来源校验；
- 根据前一步真实输出解析下一步代表输入；
- 访问门和人工等待；
- 在模型提前结束时把缺失项反馈给同一会话；
- `finally` 关闭控制会话。

Pi 不生成完整节点图或技术预算，也不为 `each` 的其余集合项重复找路。

### 3.4 证据编译

模型只根据单步骤代表轨迹补充少量语义注解；宿主从被引用的真实事件确定性生成 TaskChain。公共图只包含六类稳定节点。浏览器动作与读取合并为可验证的 `browser.perform` 能力；同构翻页或滚动编译为一个 `loop` 和一份循环体，不按事件或集合项复制节点。

### 3.5 修复—验证循环

验证协调器维护有界状态机：

```text
candidate -> validating -> verified
                     \-> repairable_failure -> repairing -> candidate(new version)
                     \-> external_blocked -> paused
                     \-> non_repairable_failure -> failed
```

规则：

1. 只有定位、绑定、来源映射、循环边界、完成条件或运行预算等本地问题进入自动修复。
2. 修复输入必须包含失败运行、失败节点、当前链路、原预执行轨迹和编译注解。
3. 修复不得再次搜索或重跑预执行；它生成新链路版本，再由正式运行器验证。
4. 每轮保存父版本、失败 run、修复原因和模型审计；旧版本与旧运行不可改写。
5. 登录、验证码、频控、访问拒绝、网络不确定和浏览器现场丢失不消耗修复次数，直接暂停。
6. 默认最多一轮本地修复。仍失败时保留证据并停止，不能以重复生成掩盖错误。

## 4. 通用来源访问门

来源访问门以公共后缀规则计算出的可注册域为站点范围；搜索、详情、验证等子域共享压力，不因协议或子域切换重置。IP、localhost 和私有域保留主机范围。实现不包含京东、淘宝、商品或评论等业务分支。策略至少包含：

- `maxConcurrent = 1`；
- 风险动作的 `minimumIntervalMs` 与随机 `jitterMs`；
- `windowMs` 与 `maxNavigationsPerWindow`；
- 根据近期累计动作增加的延迟上限；
- 外部阻断后的 `cooldownMs` 或明确 `retryAt`；
- 人工完成验证码或访问校验后的软冷却；
- 适用阶段：探索、样本验证、换输入验证、修复验证、正式复跑。

命令执行前先申请访问槽。尚未到可访问时间时，等待不计入浏览器活动预算；不得用密集 sleep、隐藏重试或并发会话抢占。收到 `rate_limited` 或访问拒绝等外部失败后，立即持久化硬冷却并熔断同站点剩余动作。人工完成验证码或访问校验只产生同站点软冷却，冷却结束后继续原运行，不把人工处理误写成失败。

站点特定的保守参数只能来自本地策略配置或用户配置数据。公共 contracts/runtime 只实现站点范围、时间窗口和访问结果语义。

### 4.1 2026-09-14 真实任务频控复盘

海尔洗碗机预执行从站点首页搜索开始，连续核验候选详情。已核验 8 个不同型号、跳过第 9 个重复型号后，第 10 个候选进入人工验证页。触发原因由本地访问事实证明为：

1. 旧访问门按完整 origin 分账，首页、搜索、详情和验证子域分别计数，跨子域访问重置了累计压力。
2. 旧策略为固定 15 秒间隔、每分钟 4 次，没有随机抖动，也不随本次任务的累计动作降速。
3. 详情页参数入口定位失败产生了额外点击，和连续打开候选详情叠加为规律性访问序列。
4. 人工验证由 `request_help` 报告，不会产生 BrowserError，因此旧代码没有把这次风险事件写入持久冷却。
5. 本地账本只能记录本工具的动作，无法知道同一浏览器 Profile 与出口网络在任务前已有多少站点访问；策略必须为未知既有压力保留余量。

修复后的默认门按站点范围累计，采用 25 秒基础间隔加 0–10 秒随机抖动、两分钟最多 3 次、十分钟内随累计动作逐步增加至最多 20 秒额外延迟，并在人工验证后软冷却 5 分钟。参数是通用保守默认值，不构成对任何站点容忍阈值的断言。

## 5. 模型质量升级

以下事实归类为探索质量失败：Pi 正常结束但未提交业务结果、提交合同不匹配、引用不存在的轨迹事件，或在没有外部阻断时遗漏明确完成条件。

处理顺序：

1. 在同一 Pi session 中发送精确缺口并继续一次，保留浏览器与轨迹；
2. 仍失败时，从当前账号可用 AgentSession 模型中选择质量级别更高的模型，开启新的 Pi session，但复用当前浏览器现场和已保存轨迹；
3. 审计记录每次选择、原因和实际 provider 调用；
4. 认证、额度、频控、人工等待和取消不属于模型质量失败，不升级模型。

## 6. 验收门

离线验证必须证明：

- 计划直接接受代表输入，生成少量步骤，并把集合消费表达为 `each`；
- Pi 提前结束时，同一 session 收到缺口反馈并继续，整个任务 authoring 的 BrowserSkill 只打开和关闭一次；
- `each` 只探索第一个代表输入，不逐项重新调用模型找路；
- 公共图只产生六类稳定节点，同构翻页次数不会增加节点数；
- 本地验证失败产生新链路版本并自动再验证，成功后才标记 `verified`；
- 修复循环不再次调用预执行浏览器搜索；
- 外部限制使循环暂停，并阻止同 origin 后续输入；
- 访问账本在新运行和服务重启后仍执行最小间隔、窗口预算和冷却；
- 公共源码没有站点名称分支；
- 所属 package 的测试和 TypeScript 检查通过。

真实任务验收按顺序执行：

1. 读取来源账本，确认不在冷却；
2. 只启动一个浏览器任务；
3. 用一个低频代表任务完成逐步骤代表探索；
4. 等访问门允许后执行一次样本复跑；
5. 若是本地错误，进入修复—验证；若是外部限制，立即暂停；
6. 样本通过后再等待访问门，使用不同输入验证；
7. 报告真实结果、访问次数、间隔、模型审计、人工等待和未完成范围。
