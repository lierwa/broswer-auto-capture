## 1. 产品目标与边界

在同一个账号管理入口，维护日常 Chrome 和专属浏览器分别使用哪些网站账号，以及系统最近一次实际检查到了什么。用户在网站登录，B-A-T 通过可复跑的只读身份检查链验证；授权扩展、浏览器连通、网站登录是三个独立事实。

Product Alignment:
- natural-language task: 在日常 Chrome 或专属浏览器登录平台，供资料查询、后台表单等不同任务复用，并可查看最近验证的账号身份。
- reusable chain boundary: 一条平台身份检查链消费当前受控浏览器会话，读取身份并返回检查结果；登录人工步骤与资源生命周期由产品层协调。
- runtime inputs: 绑定的浏览器身份、平台记录、精确检查链版本、可选预期账号身份；不读取之后变化的全局浏览器偏好。
- dynamic task outputs: 实际账号身份（可选）、已验证/明确未登录/无法确认、固定原因码和检查时间。
- generic platform capability used: 既有浏览器导航/读取/人工等待、TaskChain/Function/Branch、LangGraph、持久化与窗口所有权。
- replay model calls: 普通身份检查为 0；首次建立检查方法可复用已有准备流程并单独审计，不能每次猜登录状态。
- site/task-specific code added: no；站点 URL、定位依据和身份字段是版本化链路数据，不加入公共 runtime 的网站分支。

本期必须同时覆盖 daily 与 dedicated；专属可见/无头共用同一个账号空间，人工登录总是可见。不是密码管理器，不导入/导出 Cookie，不读取浏览器密码库，不自动扫描个人历史/既有标签以发现所有账号，不承诺所有网站都能通用识别。

一个 Profile 内同一网站的登录实际由网站决定；“账号备注”不创建隔离账号。切换同站账号必须人工在网站操作并重新检查，不能用多条列表记录伪装成多账号隔离。

## 3. 统一入口与界面

`浏览器设置 → 日常 Chrome / 专属浏览器 → 管理账号 → 同一个 Dialog 的账号管理视图`。

日常模式授权卡继续只管理 Chrome 授权，旁边/下方提供与专属模式相同的“管理账号”入口。无需实时连接也可查看/编辑已保存记录；未授权也不隐藏目录，但打开网站/检查时给出可返回的授权引导。取消授权保留目录和历史结果。

账号管理沿用一个 Dialog.Root，通过内部 view 切换内容与宽度；不叠第二层账号弹窗、不跳新 tab。顶栏“← 浏览器设置 / 浏览器账号”，下面明确当前环境与 Profile 名称。进入时固定浏览器身份，不因后台设置变更错绑。返回保留前一视图与滚动位置；关闭只关闭 UI，不暗中关闭正在登录的浏览器或写入成功。

布局：顶栏 → 当前浏览器范围 → 搜索/添加平台 → 平台列表 → 必要的操作状态。表格列为“平台、账号、最近检查、操作”。账号读取不到时为“尚未识别”；人工备注单独显示，不能当检测结果。窄屏采用既有响应式组合，不挤出竖排文字。

操作及理由：

| 操作 | 作用与可见规则 |
| --- | --- |
| 添加平台 | 输入网站地址与可选名称/备注；创建目录记录，不宣称已经登录。 |
| 去登录 / 打开网站 | 在所选浏览器的受管窗口打开平台；不自动填密码。成功检查后仍保留打开入口。 |
| 检查登录 / 重新检查 | 启动真实身份检查；按钮稳定存在，处理中显示 busy。缺检查方法时明确引导建立方法。 |
| 建立检查方式 | 首次研究已选平台的只读身份判据；系统产生链路，用户不用填写 selector/JSON。只在尚无可用检查链时出现。 |
| 编辑资料 | 当前视图内展开表单；修改名称、地址/备注。改变实际平台来源时使旧检查绑定失效，历史保留。 |
| 移除记录 | 移除目录项目；明确不退出网站账号、不删除 Profile。复用成品确认组件/当前视图确认区。 |
| 完成账号操作 | 明确结束并核验释放本次维护窗口；不等于登录验证成功。 |

不提供没有能力支撑的“批量退出所有网站”。不以删除记录代替网站退出。不显示没有动作的装饰按钮。

工作台视图跟随工作台主题；扩展 popup 继续只跟随浏览器明暗。统一主题 token、variant、字体和指针，不另建手写开关。首次读取展示 Skeleton，不能先显示“未登录”再跳成功；失败明确可重试，过期异步结果不得覆盖较新操作。

## 4. 登录确认链：真实事实的来源

### 4.1 平台检查方法的建立

没有跨所有网站可靠的统一“是否登录”API。每个平台的方法必须经过真实页面调查并成为版本化链路：

1. 明确平台和允许来源，选一个不会执行业务写入的身份页或已确认的只读身份能力。
2. 观察登录前与登录后差异，找到账户区域中能证明“当前用户”的正向身份依据；不能把公共个人主页的名字、导航栏“我的”、HTTP 200 或头像图片当作充分证据。
3. 优先采用当前浏览器适配已经支持的页面导航/读取。若选择网站公开的当前用户 API，必须先证明已具备对应受控能力与同一会话身份；禁止猜 `/me`、拼 Cookie 发请求、绕过站点或新增隐式网络 Function。
4. 编译最小链：新鲜加载检查入口 → 读取身份与已确认的未登录/挑战依据 → 纯 Function/Branch 分类 → 结构化输出。操作 URL、读取字段、判据和允许来源属于链路数据。
5. 在已登录与未登录反例验证，不为取得反例退出个人账号。使用独立受控 Profile/测试站点或已有合法记录；缺反例时保持候选，不把方法标成可靠可用。
6. 网站变化导致规则不再匹配时返回无法确认；显式修订形成新版本，不后台启动模型修复或自动覆盖原规则。

复用当前准备/编译/发布流程建立方法，不建立第二套 Agent loop 或验证 DSL。平台检查与普通任务共享通用执行引擎；身份检查结果由账号服务消费，不要求用户手工打开技术链路画布才能管理账号。若现有准备入口需最小适配，写清 producer/consumer，不能只留 TODO。

### 4.2 用户登录与检查的执行

```text
选定浏览器身份和平台
  → 去登录（取得维护会话所有权，打开 B-A-T 创建的窗口）
  → 用户处理密码、二维码、验证码
  → 回到账号管理点“检查登录”
  → 复用同一会话，加载已确认的只读身份入口
  → 读取正向身份或明确未登录证据
  → verified / unauthenticated / inconclusive
  → 持久化检查记录，UI 显示身份与检查时间
  → 用户完成账号操作，核验释放本次受管资源
```

第一版用明确的“检查登录”触发，避免用户还在输入时后台导航。关闭窗口、点击完成、返回工作台、URL 改变、Cookie 存在均不直接确认成功。可以复用有界等待，但不能无限轮询网站或后台批量检查。

正向身份必须来自本次新鲜检查，不能只读旧页面缓存的标签。检查成功但没有可靠可展示身份时，不填造用户名；契约需区分“确认身份存在”和“可展示标识”。显式预期账号与实际身份不一致时展示两者或脱敏标识并提示账号已变化，不能沿用旧账号名。

检查链输出最小结构由账号服务边界 Zod 校验，包含结果、可选身份、固定原因、检查链版本与运行引用。Function 只计算已有观察；不访问网络/浏览器/文件。未知结果不得从 Function 异常或节点失败变成 unauthenticated。

### 4.3 展示语义

| 检查事实 | UI | 是否覆盖上次成功身份 |
| --- | --- | --- |
| 尚未检查 | 未检查 | 否 |
| 没有已验证检查方法 | 尚未建立检查方式 | 否 |
| 取得明确当前身份 | 最近验证成功 · 时间；显示实际账号 | 是，保留历史 |
| 明确要求重新登录 | 需要登录 · 时间 | 不删除历史身份；当前不可确认可用 |
| 网络错误/验证码/页面变化/证据不足 | 无法确认 · 原因；可重试 | 否，独立保留上次成功时间 |
| 用户中途取消/关闭维护窗口 | 已取消/窗口已关闭 | 否 |

不把“检查完成”一律画绿。历史成功不是永久有效承诺。手动备注不影响验证状态；第一版无需“我已登录”直接盖章入口。

## 5. 通用领域模型与持久化

逻辑实体按实际需要落在现有 SQLite store，不新增另一事实库：

- BrowserIdentity：稳定本地身份；daily 绑定既有授权对应的实际 Chrome Profile/扩展实例身份，dedicated 绑定受管 Profile。mode、显示名、绝对路径都不能单独作为稳定主键。专属 visible/headless 指向同一身份。
- PlatformAccountEntry：browserIdentityId、平台来源/显示名、人工备注、可选检查链引用、revision。账号身份由检查产生。
- AccountCheck：entryId、固定浏览器绑定、精确检查链版本、runId、开始/结束时间、结果、必要且脱敏的身份字段/原因。多次检查独立记录。
- AccountMaintenanceSession：复用现有 owner/lease 及其可恢复标记，表达本次维护会话；不重复发明租约表/第二控制状态机。

可从检查记录推导的最新结果不再独立保存可漂移的 boolean。GET 查询纯读；修改与启动检查沿现有同源写入门禁。边界立即 Zod 校验；记录编辑、删除与并发检查通过 revision/冻结快照处理，迟到结果不能复活已删除记录或覆盖改绑后的平台。

刷新/服务重启后目录、历史检查和明确占用状态恢复。新授权与撤销不删目录；重新绑定不同 Chrome Profile 时创建/选中不同身份，不能把旧身份的成功状态迁移过去。

浏览器持有凭据；本地库仅保存必要账号展示数据，不保存密码、Cookie、验证码、原始认证响应或敏感页面全文。证据只保留脱敏判据摘要、链路/运行引用；检查链的常量和测试快照不得包含个人账号样本。

## 6. 浏览器会话与任务边界

查看目录、编辑备注、选择下次浏览器均不占浏览器、不受当前任务限制。只有实际打开网站/检查需要原有会话互斥；占用时明确“浏览器正在执行任务，结束后可登录/检查”，不把设置整体锁死，不自动停止任务。

日常 Chrome：仅通过已有受管扩展与原授权，在 B-A-T 创建的窗口操作；不接管原有个人标签、不复制 Profile、不读取其它 Chrome 用户。OFF 保持暂停，缺授权返回用户可点击的原生授权路线；服务不自行弹授权或代点允许。

专属浏览器：沿原 Profile 与 owner/lease。现有 startProfile→handoff 已退出 runner，必须补“在已知维护窗口上重新受控连接并检查”或复用已证明的单会话人工等待方式；选择前以固定源码及最小样本核验。不能同时打开第二个控制会话，也不能删 owner.pending 解除占用。

登录、检查、任务结果、资源清理各自记录；检查已成功但资源清理未确认时保留结果并显示维护窗口待处理。finally 释放自己拥有的控制资源；不关闭用户其它窗口。服务重启先验证原 lease/身份，无法证明时保持待核验。

本期不修改所有历史发布链路，也不对每个任务结尾添加登录 judge。需要登录的任务以后可显式 invoke 固定检查链；只有已有明确关联时才接入前置检查，不能根据域名猜哪些业务步骤需要登录。

## 7. 实施顺序与各阶段验收

| 阶段 | 交付 | 最小验收 |
| --- | --- | --- |
| P0 事实与适配核验 | 补齐 RESEARCH，选定稳定 Profile 身份与受管会话复用点 | 日常/专属身份不会串；同一专属 visible/headless 共用；两条会话适配最小样本成立 |
| P1 账号目录与 UI | contracts/store/routes，同 Dialog 的两种浏览器入口与列表、增改删 | 真实 API+SQLite，刷新/重启保留；无演示账号；主题/键盘/busy/错误/窄屏可用 |
| P2 登录维护 | 两种浏览器的打开平台、返回、完成操作与清理 | 只控自建窗口；个人标签保留；忙碌不抢占；取消/重启/清理失败保真 |
| P3 身份检查 | 平台检查方法创建/绑定、执行、身份与历史结果 | 正/反/未知/身份切换；链版本固定；不硬编码站点；普通检查 0 模型 |
| P4 Windows 集成与交付 | 真实工作台路径、受控站点、旧功能最小回归、更新文档 | 两种浏览器真实会话、同一 Profile 登录后可检查、独立 Profile 不串、重启可读；必要截图实际查看 |

实施完整闭环，不把 P1 的列表 UI 当作开发完成。优先复用成熟组件，文件≤500行、函数≤100行，阶段说明保留中文 WHY/TRADE-OFF。不得修改相邻项目、建 worktree、覆盖原 dirty work、提交或推送。

验证分层：

1. 所属单元/协议测试保护 Profile 隔离、结果分类、冻结版本、并发/取消/清理不变量；不写只复制实现的断言。
