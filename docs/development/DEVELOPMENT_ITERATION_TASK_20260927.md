## 1. 任务目标与终点

先删除当前主线不需要的功能、状态和界面负担，再修正确定性边界、缩小模型交接、接通缺失能力。最终用正式工作台的一条全新普通需求验证可复跑链路及原窗口交付，并验证同一任务的彻底删除。

唯一主线：

```text
需求对话 / 按需调查与澄清
→ 确认唯一准备计划草案
→ 同版技术投影
→ B-U 代表执行，提取现场方法与证据
→ 保存不可变来源
→ 离线编译链路草稿
→ 样本与独立复验
→ 工作台手动发布
→ 独立正式复跑
→ 结果及原窗口交付
→ 正式删除同一任务并核对残留
```

每个迭代完成所属验证后直接进入下一项，不因写完代码或通过类型检查就宣告整条主线可用。若依赖门失败，保留失败事实，只处理所属问题；能独立推进的已授权项继续完成。遇到必须由用户处理的阻塞时，交付准确断点，不能伪造成功或扩大范围。

“先删后写”指先退役多余职责和重复权威，再补必要能力。删除时为保住现有主线而做的最小接线、类型同步属于删除迭代；不能顺便重建另一套修复器、编辑器或状态机。删除收益按退出的职责与分支记录，不以删行数衡量。

| 10 | G6：正式工作台验收 | 一条全新普通需求的逐门证据及最终交付/删除结果 | 按 §7；首次与重试分开，所有必要门通过才声明该需求闭环可用。 |

F1/F4 可以由互不冲突的实现范围分别处理；依赖门未满足时不得把下游编码完成当作阶段通过。各项具体定位和最小反例见开发方案 §5–§7，按实际源码复核，不重新建立第二套协议。

**G4/G5 必须覆盖的能力清单：**

1. 访谈按需调查，来源与入口有证据，唯一草案同版投影；搜索 Timeline、题板与用户选择保持同轮对应。
2. B-U 区分当前局部 query 与业务范围，必要时沿同 Agent/Browser/job 有界续查；新业务歧义回访谈。
3. action、读取、document、目标归属和前后态经保存、裁剪、编译后仍可追溯；不把模型自报 done 当作全部证据。
4. 从 DOM 和动作提炼读取/选择/重复方法；代表执行证明方法，不预抓全集。既有 loop/condition/accumulator 支持每轮新条件、最后一轮累积、稳定键与预算边界。
5. 原动作配套保持稳定定位、一次派发、后态等待、读取及取消/恢复；等待轮询不得重放副作用。
6. 人工等待保持原 owner，暂停动作，提供聚焦、处理后继续及取消；提醒只从事实投影。
7. 交付本次真实可见原窗口和原页；TaskRun、结果、交付和清理分开。不可重开同 URL 冒充原窗口。
8. 删除覆盖本任务记录、回执、私有会话/诊断和拥有资源；共享 Profile、登录态、模型配置保留。

G4/G5 的新来源应在隔离持久化状态下经生产组件与真实受管浏览器采集。不手写 source 或伪造回执；受控现场只验证明确的基建不变量，优先复用现有现场，不能围绕用户举的“100 条”搭业务例子自证。即便局部样本通过，也不计作正式产品首次通过。

## 6. 最小验证与遇错规则

每次验证前写明：改动边界、要保护的真实不变量、选定命令/用例、预期证明、不能证明什么。验证记录复用 PROGRESS，不为每句话增加测试文件。

| 改动 | 默认最小验证 | 不得替代的证据 |
| --- | --- | --- |
| 纯文案/等价静态显示 | 定点差异及必要实际显示检查 | 不能宣称完整 UI 全阶段通过。 |
| UI/命令/合同退役 | 受影响 package 的类型检查；必要的命令拒绝和共享路径检查 | 不能以按钮消失证明后台专属路径已退出。 |
| F1/F4 | 真实 runtime/隔离 SQLite 的调用、恢复、事务故障与幂等边界 | helper 或 mock 不能替代实际生产入口。 |
| F2/F3/F5 | 实际准入与消费者的正常、缺项、拒绝、引用冲突路径 | 不能以 schema 可解析证明模型稳定或来源语义正确。 |
| G4/G5 | 生产适配器、真实浏览器及真实来源编译/执行 | 受控页面与能力样本不等于 G6。 |
| G6 | 工作台、API、SQLite、重启读取及可见原窗口 | completed、健康检查和旧 Release 不等于用户结果已交付。 |

现有 API/Workbench 的 `check` 是所属包类型检查，例如 `npm run check --workspace @browser-capture/api` 与 `npm run check --workspace @browser-capture/workbench`；只在实际受影响时选择。单个测试应指明所属文件及用例，不直接调用会遍历全部测试的包级脚本。其他 package/Python 命令先核对现有脚本与受管环境，不把示例变成批量必跑清单。

禁止未经授权运行根级 `npm test`、`npm run check`、`npm run build` 或全量测试，也不重复运行已充分验证的一组来累加通过数。需扩大范围时先说明必要性、范围和成本；用户不在场时保留该门未测，继续不依赖它的已授权项。

遇错按既有方案 §8 执行：固定版本/输入和首个错误 → 查持久化事实及真实调用 → 定位所属边界 → 最小修正 → 只重验受影响部分。禁止缺字段就加默认值、失败就加重试/字段/新状态、来源不足就猜方法、编译失败就自动重开 B-U、正常结束后加全局语义 judge。

必须暂停依赖推进的情况：

- 调用身份、发布原子性、来源同版性或必要证据尚不成立。
- 拟删除内容仍被共享主线使用，且尚未明确职责拆分。
- 新协议/字段没有唯一所有者或真实消费者；现有成熟能力是否可复用尚不清楚。
- 真实网站需用户登录、验证码或会改变业务结果的选择，而当前指令不足以决定。保留原等待及证据，不绕过、不自动代答。
- 服务/浏览器资源归属不明，或操作会影响未授权的数据/项目。

可在同边界内完成有证据的修复；若没有新证据，不重复原样运行。不要为了继续推进而隐瞒阻塞、撤掉验证门或把“不支持”包装成任务完成。

夜间出现人工等待时，保持该运行既有资源策略。只要等待 owner 仍占用浏览器，独立工作就必须不占用该浏览器、不重启其所属服务、不改变该运行状态；不能另开浏览器规避单会话约束。用户未回复不等于已处理、取消或放弃。交付时写明待用户执行的具体动作、原现场是否仍存活以及实际等待/超时/清理事实，不声称永远留存。

## 7. 正式验收纪律

只有 G1–G5 对应门已通过、所需服务与受管代码已核实加载后，才创建正式任务。开始前将需求原文、预期用户结果、选择理由、覆盖及未覆盖能力写入 PROGRESS。选择具有明确结果、可见原页交付意图的普通需求，不默认使用 Python 目录，也不把数量例子当产品测试目标。

只从正式工作台创建一条全新需求，确认、启动、发布、复跑和删除均使用实际 UI 操作；API/SQLite 用于核对事实。手动发布指工作台中的明确发布动作，不能改为自动发布或直接 API 注入。不得开发脚本改稿、注入链路、补造 source，或用旧任务/Release 代验。

逐门分别记录：需求/必要搜索与题板、唯一草案确认、首次 B-U、首编译、样本、独立复验、手动发布、正式复跑、UI/API/SQLite、可见原窗口、重启后的持久化事实、同任务彻底删除。记录版本和本次运行引用，普通复跑模型调用仅允许显式 `llm` 节点。

先观察原窗口真实交付并记录结果，再验证必要的重启/清理行为，最后从 UI 删除该任务。服务重启不能毁掉尚未核验的活窗口再用新窗口补证。删除后只保留安全的验证摘要，明确原 ID 已不可再查；不通过维护脚本替产品删残留后宣布删除门通过。

首次失败保持为失败。定点修复后的同版诊断/重试只能另记重试结果，不能重命名为首次；不再建立第二条任务洗掉首次失败。缺证需要重新采集时遵守原方案的显式启动要求，旧来源不改写。人工等待、复杂重复、多步及清理错误没有自然发生，就列未测，并引用此前所属能力证据，不能假称一条需求覆盖全部系统。

任一首次门失败后，该条需求的“全链一次通过”结论永久为失败，后续同版诊断不能将 G6 的一次通过门关闭为通过。所属代码迭代可凭对应验证交付，但正式首次验收必须单独报告失败；是否另起全新验收留给后续明确指令，本次不自动创建第二条需求。

- [ROADMAP](ROADMAP.md)：唯一下一门及依赖；[RESEARCH](RESEARCH.md)：Product Alignment、必要 Reuse Assessment 与验证设计。
- [开发方案](INFRASTRUCTURE_MAINLINE_DEVELOPMENT_PLAN_20260927.md)：只有设计和退出条件确实变化时同步，不能悄悄降低门槛。

最终报告必须分开说明：

1. **已删除：** 哪些整段职责已退出，哪些只减少展示，哪些实际无需修改。
2. **已修复并验证：** 哪个真实不变量、什么入口、什么证据。
3. **失败/阻塞：** 首个失败及所属阶段，现存安全产物，确切需要的外部条件。
4. **未测/未完成：** 未运行门和未覆盖分支，下一项可直接开始的动作。
5. **现场：** checkout/HEAD、dirty 保留、服务身份和是否运行、任务及原窗口状态；不关机、不擅自提交或推送。

只有删除、基础设施、能力和正式任务的必要门均有相应证据，才能宣布本迭代全部完成。没有通过 G6 时，可以准确交付前面已完成的迭代，但必须写明产品全链验收未通过。
