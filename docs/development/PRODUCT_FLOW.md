# 产品流程与工作台交互基线

更新：2026-09-13。性质：产品理解与交互约束，不表示后端能力已实现。任务链路公共边界见 [自然语言浏览器任务链路架构基准](TASK_CHAIN_ARCHITECTURE.md)，首次探索和轨迹编译见[重构实施说明](TASK_CHAIN_AUTHORING_REDESIGN.md)。目标产品由浏览器扩展主前端、Web 辅助管理与 Node 服务端组成，职责见 [产品运行架构方向](PRODUCT_ARCHITECTURE.md)。统一开发入口见 DEVELOPMENT_BASELINE.md；原型保留为布局基线，完整业务状态按 UI_STATES.md 随功能开发验收。

## 1. 产品起点与参考机制

用户的一句话是访谈起点，不是执行计划。需求访谈按最终结果选择领域知识，形成可审阅需求草稿。草稿确认后生成声明动态输入输出、步骤依赖、业务限制和完成条件的任务计划；需要来源发现时，它只是计划中的普通步骤。用户为某一步提供代表输入并明确启动后，Pi AgentSession 才使用 BrowserSkill 完成真实代表任务，B-A-T 从工具轨迹和字段来源编译低层链路。需求草稿、任务计划、任务链路和运行结果分别拥有版本和事实来源。

参考 `domain-analysis` 的现行实现（只读核验 master / 93a57b6）：`categoryInterviewModule.ts` 将消息、建议、确认决策、待决事项、草稿版本分别保存；`confirmTaskDraft` 仅接受最新可确认草稿，确认后才独立生成正式任务。`crawlPlanningModule.ts` 独立运行规划与计划确认；`InterviewThread.tsx` 使用持续对话。这是机制参考，不复制相邻项目的数据库或业务实现。

采用 `grill-with-docs` 的逐问、推荐答案、依赖决策与随答沉淀原则。工程 glossary 记录术语；产品需求文档记录用户范围与决策。不是把每次回答写成工程 ADR，也不是让固定 schema 限制用户表达。

## 2. 九个阶段的职责

| 阶段 | 输入与实际工作 | 产物 | 确认条件 / 失败回路 |
| --- | --- | --- | --- |
| 1 需求访谈 | 初始描述、完整历史、已确认决策；按最终结果使用对应领域知识，每轮解决一个关键取舍；可现场核实的事实留作调查 | 消息、待决事项、需求决策、持续修订草稿 | 目标、输入、约束、依赖、可观察完成标准、调查事项和权限边界明确；不按固定轮数判断完成 |
| 2 确认需求草稿 | 审阅目标、上下文与输入、范围、限制、步骤依赖、完成标准、调查事项和授权边界 | 用户确认的草稿版本及任务范围 | 只确认当前版本；新输入先退出可确认状态；确认不产生浏览器执行授权 |
| 3 生成任务计划 | 依据已确认需求识别可复用步骤与链路组合，声明输入、输出、依赖、业务数量和完成条件 | 版本化 TaskPlan 与 digest | 计划生成不打开浏览器，也不产生执行授权；来源发现按任务需要成为普通步骤；技术预算稍后由图推导 |
| 4 确认代表探索 | 用户审阅步骤范围、业务限制和权限，为当前步骤提供或选择符合动态合同的代表输入并启动探索 | 绑定需求/计划/步骤/输入的探索授权与 BrowserRecord | 该动作只授权本次代表探索，不授权整批复跑；仅一个实际浏览器任务 |
| 5 动作探索 | 已授权步骤及代表输入；AI Connect 选择的模型由 Pi AgentSession 通过受控 BrowserSkill 完成实际任务 | 真实业务结果、动作后观察、类型化工具轨迹、字段来源、终止依据和模型审计 | 登录态失效时显式请求人工；失败不制造可复用链路；BrowserSkill 会话 finally 回收 |
| 6 生成链路版本 | 模型只补充输入/循环/来源/完成/复用注解；宿主从真实轨迹确定性生成唯一现有 IR | 步骤对应的候选链路、推导技术预算、编译证据及覆盖声明 | 无来源字段、临时 ref、隐藏 LLM 或不支持能力不可编译；图形不是执行能力证明 |
| 7 验证链路 | 先以代表输入执行候选，再在声明覆盖范围内换输入，以普通运行器证明复用 | 两个独立运行的输入输出、终止原因、调用审计和通过/失败结论 | 失败回到该步骤探索；探索成功或单个样本成功都不等于 verified |
| 8 授权执行与验收 | 用户核对已验证链路、业务数量、推导技术预算和风险后授权；系统按固定版本执行组合并保存检查点 | 版本绑定的执行授权、独立运行、动态输出、错误和审计 | 依据真实完成条件报告完成/部分完成；技术消费不会在恢复时重置 |
| 9 复跑、恢复与修复 | 新输入、原检查点或受影响链路 | 新运行、同运行恢复记录或修复后验证的新版本 | 复跑独立；恢复同运行且核验浏览器；漂移暂停，用户发起模型修复 |

这九个阶段不是九个按钮或线性导航向导。每个步骤可以分别探索、编译和验证；只有全部所需链路 verified 后，计划才能获得整批执行授权。计划依赖和链路内部节点是两层结构。

## 3. 需求对话、决策与版本

- 首屏进入持续需求对话，支持自由输入、推荐答案、补充、纠正、追问、取消和重试；不使用一次性需求弹窗。
- 每轮一个关键取舍，推荐项说明原因。不选推荐项也能自由表达；预选不等于授权。
- 草稿包含目标、来源范围、内容、完成标准、约束、已确认决策、待决事项和版本。消息不是草稿；建议不是用户决策。
- 完整成功且边界校验通过的轮次才提交决策/草稿；取消、失败和迟到结果不能覆盖新版本。
- 受支持的浏览器自动化 Markdown 需求确认后可以生成 TaskPlan；生成完成不等于浏览器授权。每次代表探索由用户提交步骤输入明确启动；全部链路验证后，再单独授权计划复跑。
- 确认后再修改：保留历史与结果，将依赖旧需求的计划标为待复核。活动运行仍绑定原版本，不能用旧授权执行新范围。
- 产品会话是事实源，模型线程只是执行上下文；刷新恢复和并发修订校验属于正式实现门。
- 当前访谈通过 AI Connect 绑定项目显式选择的本机账号和模型，Main 由 Pi AgentSession 管理模型会话；访谈只注入项目私有 Skill 与本轮业务事实，工具和全局资源为空。首次探索复用同一账号/模型选择，但创建独立的受控 Pi AgentSession 并只暴露本次授权的 BrowserSkill 工具。AI Connect React 提供完整 Timeline 与 Composer，Fastify 及 Drizzle/SQLite 保存业务会话事务。消息、决策、待决事项、结构化草稿及确认版本按任务持久化；左侧任务选择统一切换四视图，不共享访谈状态。全局与页面信息承载见 [工作台布局](WORKBENCH_LAYOUT.md)，实现与证据边界见 [需求对话机制](INTERVIEW_UI.md)。
- BCT 与 opencode Examples 的 Agent 对话遵循同一套[公共宿主 surface 规范](../../../opencode/docs/platform/ai-connect-host-surface-parity.md)：生命周期和事件投影、Timeline、Composer、模型设置、Question 注册与答复行为由公共包负责。BCT 只拥有浏览器抓取 Skill、Workflow、业务状态和宿主命令接入；主题色、助手名称和图标可以配置，公共布局、状态与交互不能分叉。
- 当前访谈注册单选与复选 Question：互斥方向用单选，同轴且可并存的条件用复选；两者都可携带同面板自由补充，并使用同一 waitpoint identity、revision 和提交生命周期。历史开放题继续按原 Surface 和答复只读恢复。确认需求仍是独立操作，不授权计划生成或抓取。

## 4. 来源、计划与链路

需要来源发现的任务由普通计划步骤输出候选、观察证据和覆盖缺口；不需要来源研究的表单、播放、后台配置等任务不会被强制增加搜索阶段。提供 URL 只是动态输入，只有浏览器运行中的 fresh observation 才能支持页面事实。新增来源范围或扩大预算需要新计划或新授权。

计划步骤包含目标、依赖、动态输入输出、终止条件、业务限制及链路状态。上游步骤可以产生一个输入集合，下游步骤通过链路调用逐项复跑同一条参数化链路；不得为每项输入复制节点图或逐项重新让模型找路。链路拆分由输入输出边界、探索证据和复用范围决定，不按网站或业务实体固定数量。任务的字段、数量和页面语义以各自确认草稿及链路版本保存，不能成为平台公共类型或其他任务的默认值。图迁移、浏览器命令、活动时间、调用深度和显式 LLM 等技术预算由编译器从图和节点能力推导。

Plan 的按需取证解决“在哪里、需要何种访问条件、是否具备计划可行性”，核验候选、代表样本和枚举依据；计划步骤解决每一步要达到什么结果。授权后的 Pi 探索解决“具体怎样操作并实际得到什么结果”，B-A-T 再依据真实轨迹和字段来源固化任务链路。访谈以已确认结构需求交接，不能把入口发现或全量枚举变成用户提供链接的义务。浏览器取证和执行都受单任务、会话回收和人工登录边界约束。系统先用 BrowserSkill Profile 访问任务所需的实际来源；来源内容与入口能力可用时，由该 observation 建立访问前置证据并自动继续。只有真实登录、验证码或权限阻断才通过 BrowserSkill `request-help` 转入人工等待；`Done` 只交还控制权，完成后必须 fresh observe 并以实际来源能力决定继续或保持阻塞。保存脱敏证据引用，不将登录态、验证码或敏感页面原文写入日志/Git。

链路查看必须呈现普通动作、条件分支、循环、检查点、输入参数和完成标准，并能回看编译证据与输出字段来源。普通节点不隐式调用模型；访谈、首次探索、编译注解、用户修复和显式 LLM 节点分别审计。没有审计记录显示未接入，不显示零次；账号/供应商用量错误与链路技术预算分开显示。

## 5. UI 信息架构

- 保留工具导航、任务摘要和可切换主工作区。沿用深浅主题、语义 Token、Radix 与 React Flow，采用紧凑专业工作台布局。
- 主视图：需求对话、任务计划、任务链路、运行结果；设计系统仅保留为工程实现规范，不进入业务导航。
- 需求页：公共 Timeline 按统一生命周期呈现安全的活动状态、工具事件、消息、当前问题和输入；草稿以消息文档卡和当前版本入口呈现，完整内容与版本按需打开，旧版本查看不覆盖当前状态。不得暴露原始 chain-of-thought、凭据或敏感诊断。
- 计划页：显示版本、步骤依赖、动态输入输出、完成条件与业务限制；每一步提供或选择代表输入后可明确启动探索。候选图生成后再显示推导技术预算；全部链路 verified 后才开放整批执行授权。
- 链路页：步骤切换、常驻大画布、节点详情。缩放和节点检查不需要需求确认；区分样例、草案、已验证版本。
- 结果页：运行、部分结果、产物和审计；无运行展示真实空态，生产入口不挂载结构样例。
- 门禁限制副作用，不限制查看。切换视图不修改业务阶段、不自动跳转、不清空输入和节点选择。
- Tabs 的焦点与激活分离：方向键移动焦点，Enter/Space 或点击激活；查看上下文不触发执行动作。
- 宽屏详情并排，空间不足时改右侧抽屉，任务列表在窄屏使用左侧抽屉；不把所有长详情堆到主区下方，也不通过隐藏画布解决空间问题。支持键盘 Tabs/输入/节点、主题对比和 reduced motion；覆盖状态和实测边界分别见 UI_STATES.md、PROGRESS.md。

## 6. 反例与验收

| 场景 | 必须发生的行为 |
| --- | --- |
| 只输入“抓冰箱” | 开始访谈，不直接生成计划 |
| 自由纠正范围 | 保存原文并重新澄清，不能确认旧草稿 |
| 需求确认且计划尚未生成 | 可生成 TaskPlan；此时不打开浏览器，也不声称来源已核验 |
| 已有登录态可访问代表输入 | 探索中的 fresh observation 直接继续，不产生人工等待 |
| 探索、验证或授权执行遇到登录/验证码 | 显式 human 节点保留浏览器现场并进入人工等待；Done 后重新观察，满足恢复条件才继续；协助超时不自动重试 |
| 浏览器导航/读取命令失败 | 当前运行立即进入可恢复暂停，保存步骤、记录和剩余输入；不把传输失败当作可修链错误，也不自动重复访问同一来源 |
| fresh page 明确显示访问限制 | Chain 模型以 typed `request_help(access)` 请求人工；人工返回后 fresh observe，仍受限则继续暂停，不通过站点业务跳转规避限制 |
| 未确认就查看链路 | 可切换、缩放、查看已有历史节点；不可启动探索或执行 |
| 查看别页再返回 | 保留消息、输入、决策及草稿版本 |
| 修改已确认需求 | 新修订使旧确认失效，历史仍可查看 |
| 轮次失败/取消 | 不提交成功草稿，允许有界重试 |
| 页面结构漂移 | 暂停受影响链路，保存检查点，等待修复授权 |

验收按 INTERVIEW_UI.md 与 PROGRESS 区分真实多轮访谈、UI 交互与浏览器执行门，不以离线节点 fixture 冒充浏览器通过。
