# 产品流程与工作台交互基线

更新：2026-09-06。性质：产品理解与交互约束，不表示后端能力已实现。统一开发入口见 DEVELOPMENT_BASELINE.md；原型保留为布局基线，完整业务状态按 UI_STATES.md 随功能开发验收。

## 1. 产品起点与参考机制

用户的一句话是访谈起点，不是执行计划。先通过持续对话形成可审阅需求草稿，再真实搜索、检查抓取源，最后根据来源证据制定抓取计划。需求草稿、来源调研、计划、可执行链路、运行结果分别拥有版本和事实来源。

参考 `domain-analysis` 的现行实现（只读核验 master / 93a57b6）：`categoryInterviewModule.ts` 将消息、建议、确认决策、待决事项、草稿版本分别保存；`confirmTaskDraft` 仅接受最新可确认草稿，确认后才独立生成正式任务。`crawlPlanningModule.ts` 独立运行规划与计划确认；`InterviewThread.tsx` 使用持续对话。这是机制参考，不复制相邻项目的数据库或业务实现。

采用 `grill-with-docs` 的逐问、推荐答案、依赖决策与随答沉淀原则。工程 glossary 记录术语；产品需求文档记录用户范围与决策。不是把每次回答写成工程 ADR，也不是让固定 schema 限制用户表达。

## 2. 十个阶段的职责

| 阶段 | 输入与实际工作 | 产物 | 确认条件 / 失败回路 |
| --- | --- | --- | --- |
| 1 需求访谈 | 初始描述、完整历史、已确认决策；每轮解决一个关键取舍，附建议与原因；事实自己调查 | 消息、待决事项、需求决策、持续修订草稿 | 关键取舍明确；不按固定轮数判断完成 |
| 2 确认需求草稿 | 审阅目标、来源范围、内容、限制、完成标准 | 用户确认的草稿版本及任务范围 | 只确认当前版本；新输入先退出可确认状态 |
| 3 真实来源调研 | 依据确认草稿搜索、打开页面、检查代表样本和入口 | URL、观察时间、可提供字段、枚举依据、访问限制、覆盖缺口 | 证据足以规划；不足则带证据返回需求讨论，不静默缩减目标 |
| 4 制定抓取计划 | 组合范围、来源证据和覆盖，拆分依赖步骤 | 来源绑定、步骤输入输出、预算、终止条件、风险 | 绑定需求版本及来源证据；不把模型猜测标记为已验证 |
| 5 确认计划并启动 | 用户核对来源、范围、预算和风险 | 版本绑定的执行授权与排队记录 | 确认需求不等于授权整批抓取；仅一个实际浏览器任务 |
| 6 逐步真实探索 | 授权步骤及代表输入；模型通过受控 BrowserSkill 操作页面 | 观察证据、样本结果、定位与终止依据 | 登录/验证码由用户处理；失败不制造可复用链路 |
| 7 生成链路版本 | 将探索证据转成节点、连线、循环、参数与校验 | 步骤对应的链路版本及覆盖声明 | 节点落到已支持动作；图形不是执行能力证明 |
| 8 验证链路 | 在声明覆盖范围内换输入，以代码运行固化普通节点 | 验证输入输出、终止原因、调用审计、通过/失败结论 | 失败回到该步骤探索；原样本成功不等于通用复用 |
| 9 执行与验收 | 在授权范围执行剩余输入，保存检查点和部分结果 | 独立运行、来源数据、真实覆盖、错误和审计 | 依据真实完成条件报告完成/部分完成，不以动画替代 |
| 10 复跑、恢复与修复 | 新输入、原检查点或受影响链路 | 新运行、同运行恢复记录或修复后验证的新版本 | 复跑独立；恢复同运行且核验浏览器；漂移暂停，用户发起模型修复 |

这十个阶段不是十个按钮或线性导航向导。6–8 可按步骤交替推进：先枚举商品并验证，再把实际 URL 输入详情和评论步骤。访谈可做辅助调查，但阶段 3 必须对确认范围形成正式来源证据。计划依赖和链路内部节点是两层结构。

## 3. 需求对话、决策与版本

- 首屏进入持续需求对话，支持自由输入、推荐答案、补充、纠正、追问、取消和重试；不使用一次性需求弹窗。
- 每轮一个关键取舍，推荐项说明原因。不选推荐项也能自由表达；预选不等于授权。
- 草稿包含目标、来源范围、内容、完成标准、约束、已确认决策、待决事项和版本。消息不是草稿；建议不是用户决策。
- 完整成功且边界校验通过的轮次才提交决策/草稿；取消、失败和迟到结果不能覆盖新版本。
- 确认需求之后进入来源调研，不直接出现可执行计划。用户确认计划并启动后，在预算内自动探索、生成、验证并继续剩余范围。
- 确认后再修改：保留历史与结果，将依赖旧需求的调研/计划标为待复核。活动运行仍绑定原版本，不能用旧授权执行新范围。
- 产品会话是事实源，模型线程只是执行上下文；刷新恢复和并发修订校验属于正式实现门。
- 当前访谈已接入真实 Codex App Server、私有 skill、assistant-ui、Fastify 与 Drizzle/SQLite 会话事务。消息、决策、待决事项、结构化草稿及确认版本按任务持久化；左侧任务选择统一切换五视图，不共享访谈状态。全局与页面信息承载见 [工作台布局](WORKBENCH_LAYOUT.md)，实现与证据边界见 [需求对话机制](INTERVIEW_UI.md)。

## 4. 来源、计划与链路

来源调研至少展示查询意图、实际 URL、观察时间、字段、枚举/分页方式、访问限制、覆盖缺口及采纳理由。候选、已观察、受限、不可用分别标记；搜索命中不等于可抓取。新增来源或扩大预算需重新确认。

计划步骤包含目标、来源引用、依赖、输入、输出、终止条件、预算及链路状态。“枚举商品”输出稳定来源键和 URL；详情/评论依赖该输出。范围为整个品类时，也可先发现符合口径的品牌/店铺集合，再分批枚举与采集。链路拆分由实际依赖、探索证据和复用边界决定，允许合并或拆分，不固定数量，不要求用户预先交齐各层链接。首版规模验收任务要求每商品页面最多 100 条评论、默认排序、不足记录原因；产品任务的数量、字段和范围以各自确认草稿为准。计划结构样例不能成为任意当前需求的正式计划。

来源调研解决在哪里及是否可行，核验候选、代表样本与枚举依据；正式计划再组织完整范围的批量枚举和采集。访谈以已确认结构需求交接，入口发现和页面未知留给系统调查；不能把全量枚举前置成用户提供链接的义务。操作探索解决具体如何执行。浏览器调研也受单任务、会话回收和人工登录边界约束。保存脱敏证据引用，不将登录态、验证码或敏感页面原文写入日志/Git。

链路查看必须呈现普通动作、条件分支、循环、检查点、输入参数和完成标准。普通节点不隐式调用模型；访谈、首次探索、用户修复和显式 LLM 节点分别审计。没有审计记录显示未接入，不显示零次。

## 5. UI 信息架构

- 保留工具导航、任务摘要和可切换主工作区。沿用深浅主题、语义 Token、Radix 与 React Flow，采用紧凑专业工作台布局。
- 主视图：需求对话、来源调研、抓取计划、抓取链路、运行结果；设计系统仅保留为工程实现规范，不进入业务导航。
- 需求页：完整对话、当前问题和输入居主位；草稿以消息文档卡和当前版本入口呈现，完整内容与版本按需打开，旧版本查看不覆盖当前状态。
- 调研页：证据列表和覆盖检查；未开始显示待查事项，只有实际观察后才显示结论。
- 计划页：步骤依赖、输入输出、完成条件及版本；确认启动受真实证据门约束。
- 链路页：步骤切换、常驻大画布、节点详情。缩放和节点检查不需要需求确认；区分样例、草案、已验证版本。
- 结果页：运行、部分结果、来源和审计；无运行展示真实空态，结构样例由用户主动展开且明确标注。
- 门禁限制副作用，不限制查看。切换视图不修改业务阶段、不自动跳转、不清空输入和节点选择。
- Tabs 的焦点与激活分离：方向键移动焦点，Enter/Space 或点击激活；查看上下文不触发执行动作。
- 宽屏详情并排，空间不足时改右侧抽屉，任务列表在窄屏使用左侧抽屉；不把所有长详情堆到主区下方，也不通过隐藏画布解决空间问题。支持键盘 Tabs/输入/节点、主题对比和 reduced motion；覆盖状态和实测边界分别见 UI_STATES.md、PROGRESS.md。

## 6. 反例与验收

| 场景 | 必须发生的行为 |
| --- | --- |
| 只输入“抓冰箱” | 开始访谈，不直接生成计划 |
| 自由纠正范围 | 保存原文并重新澄清，不能确认旧草稿 |
| 需求确认但尚未查源 | 调研待开始，计划不可确认执行 |
| 搜索命中但样本受限 | 证据标记受限，不能宣告已覆盖 |
| 未确认就查看链路 | 可切换、缩放、查看样例节点；不可启动执行 |
| 查看别页再返回 | 保留消息、输入、决策及草稿版本 |
| 修改已确认需求 | 新修订使旧确认失效，历史仍可查看 |
| 轮次失败/取消 | 不提交成功草稿，允许有界重试 |
| 页面结构漂移 | 暂停受影响链路，保存检查点，等待修复授权 |

验收按 INTERVIEW_UI.md 与 PROGRESS 区分真实多轮访谈、UI 交互与后续未完成的来源/执行门，不以节点样例冒充浏览器通过。
