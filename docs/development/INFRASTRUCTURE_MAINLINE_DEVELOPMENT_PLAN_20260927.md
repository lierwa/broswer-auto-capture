## 1. 目标、范围和完成含义

### 1.1 要达到的状态

1. 非 LLM 环节对固定版本、输入和已记录事实，产生确定的结果或明确错误；不猜缺项、不混用调用、不偷偷换目标。
2. LLM 只提交必须由它判断的语义和方法。宿主已有的标识、摘要、来源、执行事实、值装配和状态由宿主生成。
3. 模型输出错误、缺证或服务失败时，系统停在对应边界；上一份有效产物保留，未通过的候选不推进。
4. 原生 action 的配套能力能从真实入口被调用，输出可以继续进入保存、编译和普通执行器；每段都有责任明确的生产者和消费者。
5. 普通复跑使用固定链路和本次输入；模型调用只来自显式 `llm` 节点，并保留审计。

“稳定”不表示网页永远不变。网页、焦点或文档发生变化时，需要由适配器核验支持的条件；不满足则明确失败、等待或进入既有恢复路径。等待后态不得重派已有副作用。

### 1.2 本轮边界

- 本地任务清理已完成。本轮只执行用户要求的完整删除清单整理；下文各实施卡是后续开发依据，不表示本轮已开始改生产代码。
- 沿用当前 checkout，保留所有已有未提交改动；不建 worktree，不 reset/clean，不提交或推送，不改相邻项目。
- 不增加站点、会员、业务数量或示例专用流程。访问资格是某项需求可能出现的歧义，由访谈根据目标处理。
- 不重做已有新页恢复和单次 headless 开关，不增加桌面提醒等旁路功能；声音不在开发和验收范围。
- 不恢复旧模型计划或旧来源执行兼容；清空后的旧任务、旧 Release 不能作为新开发的执行输入。
- 不承诺一次普通任务能覆盖所有能力。正式主线验收、重复处理能力、人工等待和清理错误等证据分别记录。

- **共享能力边界：** 普通编译的 F3 选择注解、编译失败保存 gap、同一来源离线重编译、首次 `createTaskDraft`、验证和手动发布继续保留。不能因两处都叫“模型拒绝”就合并或误删。
- **三个情境：** 尚无链路时显示真实失败阶段及已有产物；草稿试跑失败时保留草稿与失败运行、禁止发布；已发布运行失败时保留 Release 与独立失败运行。当前不提供智能改链，也不把改代码/selector 的任务交给普通用户；开发先修对应基建或能力，新执行不改写旧失败。业务理解错了仍可回需求对话。
- **退出证据：** 主线命令不再依赖调整模块，旧调整请求在边界明确拒绝且不落入默认取消分支；工作台无失效入口，失败查看/等待/清理仍可达；首次草稿创建、验证门和手动发布保持可用；专属合同和生产消费者成对移除，不能只加隐藏开关留整套热路径。
- **最小验证：** 按实际删改包核对类型和调用面；只验证删除后的命令拒绝、共享草稿/发布及保留失败处理不变量。不跑根级/全量测试，不启动新的业务任务证明“删除成功”。
- **重新考虑条件：** 当前通用主线和真实方法能力通过既定门，且有正常使用中具体、可定位的调整需求时，再单独设计；不以恢复旧实现作为默认方案。

本轮没有删除第三方库。后续删减复用现有 Radix/React Flow、Pi、浏览器组件、SQLite 和 LangGraph，必要能力不以自写替代品补回。实施前的 Product Alignment 应明确“普通用户创建并复跑任务”的边界、运行参数和动态结果，并逐项说明删除没有改变普通复跑的模型调用规则。

## 6. 模型字段减法与新增字段准入

### 6.1 逐项处理真实交接

| 交接 | 模型需要提供 | 宿主应推导或内部保留 | 本轮后的处理顺序 |

| 原生 action | 动作及必要参数、现场目标方法 | registry schema、实际回执、document、派发计数 | 沿用原接口；不得让模型复制宿主已经知道的成功事实。 |

### 6.2 每次删改字段的固定步骤

1. 写出真实线上请求和响应的字段表；区分模型生成、模型可见、宿主内部和持久化。Markdown 机器段、JSON 字符串的内层同样列出。
2. 对每个拟删除字段注明唯一替代事实和推导位置。若宿主没有可靠替代，不先删除再在下游补默认值。
3. 同时修改对应提示/工具 schema、准入、投影和消费者；检查原字段是否仍被日志、恢复或 UI 当作权威。
4. 只保留一份事实源。模型视图可以简化，宿主内部用于版本、来源和审计的证明不得因此丢失。
5. 核验正常结果、缺项和拒绝三条真实边界；记录实际删去的重复声明和未消除的风险，不用顶层字段数证明成功。

### 6.3 新字段、新类型或新状态必须回答

- 它承载哪个现有事实无法表达的职责？能否从既有输入推导？
- 唯一所有者是谁？哪个真实入口产生，哪个真实消费者读取，什么时候保存？
- 至少哪两类浏览器任务需要它？是否把某个站点、业务数量或任务实例写入公共源码？
- 缺失、冲突、恢复和版本变化时怎样处理？是否制造第二份权威？
- 能否用现有 union、binding、gap、事务或适配面解决？为什么不能？
- 本次会删除或合并哪些重复字段/分支？若没有，是否已证明新增能力确实不可缺？

以上无法说明时，先调整设计。字段少并不意味着把错误藏进字符串；F3 的成功与缺证必须有可解析的表达，但应复用原结果边界。

## 8. 遇错时的固定处理方法

1. **先冻结事实。** 记录当前阶段、版本、输入引用、运行身份、首个错误及已有持久化结果；不先重跑、不覆盖来源。
2. **先确定责任。** 查真实生产者和消费者，区分输入非法、能力缺失、接线错误、运行器缺陷、外部条件和模型服务错误。源码结构优先 CodeGraph，日志和明确字符串再定点检索。
3. **找到最小反例。** 使用失败阶段的真实入口；纯解析用解析器，调度用运行器，事务用隔离 SQLite，浏览器行为用真实浏览器。避免为解释一个错误先搭第二套实现。
4. **先复用或删除。** 检查已有方法是否未使用、所有权是否重复、字段是否可推导。只有现有表达确实不足时才按第 6.3 节新增。
5. **只改所属边界。** 记录修改为何能消除首个错误，以及它不会把错误推迟到下一段。编译错误修编译，模型缺项不能靠默认值消失；来源确实缺证时保留 gap，需要用户从工作台显式发起新采集 job，旧来源不改写，新 job 不替代旧首次结果。不得自动整项重探索掩盖编译错误。
6. **只补必要证明。** 保护真实协议、错误路径或回归不变量才新增所属包测试；新增测试须说明它区分哪两种实际行为。模拟 fixture 通过只能标为局部证据。
7. **再推进一次。** 仅重复失败的最小验证。通过后停止可选重复，进入下一门；有新错误则用新事实重新定位，不连续扩字段、加重试或增加模型调用。

持久化、错误分类和恢复规则应在同一个所属边界内闭合。禁止新增全局语义 judge 来替代缺失的现场调查，也禁止把合法 TaskRun 因额外证明缺失改判失败。
