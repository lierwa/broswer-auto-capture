# 稳定通用任务链节点迭代说明

日期：2026-09-14
状态：代码与本地定点验证完成；真实业务任务尚未跑通
范围：公共契约、轨迹编译、正式运行、访问频控与真实复跑

## Product Alignment

```text
Product Alignment:
- natural-language task: 完成任意已授权的浏览器交互，并把成功方法沉淀为可换输入复跑的任务链
- reusable chain boundary: 一条链表达少量有业务意义的步骤；重复页面操作由有界循环复用同一能力，不按工具事件展开节点
- runtime inputs: 已确认需求声明的动态输入、数量上限和前序链输出
- dynamic task outputs: 任务输出合同要求的值、制品引用、完成证据与类型化失败
- generic platform capability used: 通用能力节点、显式模型节点、分支、复合循环、子链调用、终点、LangGraph、BrowserSkill 与持久检查点
- replay model calls: 只允许来自链路中显式 llm 节点；普通浏览器和数据任务为 0
- site/task-specific code added: no
```

## 1. 本轮解决的问题

旧编译器把一次成功探索里的点击、读取、观察和检查点逐条翻译成节点。探索越曲折，链越大；一次 94 个节点、14 个模型节点的产物本质上是执行记录回放。它有三个根本问题：

1. 工具事件数量决定节点数量，无法表达“重复同一方法直到完成”。
2. 某次探索产生的临时页面状态被固化，换输入或模型输出略有变化就断链。
3. 浏览器动作、观察、数据操作、人工等待、检查点和输出发布都被提升为节点类型，平台词汇会随任务增长。

本轮把公共节点收敛为稳定控制结构，把浏览器动作和数据处理降为可注册能力，把站点、页面、业务对象和字段保留在任务版本数据里。

## 2. 官方设计核准

本轮采用 Dify 与 Coze 官方实现共同体现的边界：

- Dify 的工作流生成器只让模型提供有意义的节点数据，图包装、节点元数据、布局和校验由宿主补全；工具节点通过 provider、tool、配置和参数调用能力，而不是为每个业务动作发明节点类型。
- Dify 把 iteration 和 loop 作为容器节点，循环体是显式子图；重复次数不会复制循环体。
- Coze 的通用运行节点声明输入类型与来源、输出类型与来源、配置；批处理和循环是带内部工作流的组合节点，并由统一运行框架处理中断与恢复。

来源：

- [Dify workflow builder prompt](https://github.com/langgenius/dify/blob/main/api/core/workflow/generator/prompts/builder_prompts.py)
- [Dify workflow planner prompt](https://github.com/langgenius/dify/blob/main/api/core/workflow/generator/prompts/planner_prompts.py)
- [Dify iteration quick start](https://docs.dify.ai/en/guides/workflow/node/iteration)
- [Coze workflow node backend design](https://github.com/coze-dev/coze-studio/wiki/11.-Add-new-workflow-node-types-(backend))

由此确定 B-A-T 的边界：模型负责识别少量语义步骤和数据关系；宿主负责生成合法图、绑定能力、校验合同、控制循环、持久化与恢复。

## 3. 三层模型

### 3.1 节点层

公共节点只表达控制结构：

| 节点 | 作用 | 不拥有的内容 |
| --- | --- | --- |
| `capability` | 调用一个版本化能力，输入输出均有合同 | 站点、商品、评论、表单等平台类型 |
| `llm` | 明确调用模型并校验结构化输出 | 隐式推理、普通节点内部模型调用 |
| `branch` | 根据已有值选择出口 | 浏览器定位或数据抓取 |
| `loop` | 有界重复内部子图并累计结果 | 展开的 N 份动作节点 |
| `invoke` | 调用已冻结的另一条链 | 临时复制子链内容 |
| `terminal` | 结束并返回结果、状态和证据 | 单独的 emit 或 checkpoint 步骤 |

链输入是链合同，不需要 `start` 节点。人工等待、保存检查点、浏览器会话、频控等待和事件发布属于运行生命周期，不是用户编排的节点。

### 3.2 能力层

能力通过注册表解析，节点只保存以下公共信息：

- `name`：稳定能力名，例如 `browser.perform`、`data.transform`；
- `version`：能力合同版本；
- `input`：从链输入、前序节点或循环上下文绑定的值；
- `config`：任务版本数据，必须通过该能力自己的 Zod 配置校验；
- `effect`：`read`、`idempotent_write` 或 `external_write`；
- `timeoutMs`：单次能力调用上限；
- `outputContract`：调用结果合同；
- `writes`：需要写入循环或链变量的结果路径。

`browser.perform@1` 的配置可以描述一次可验证的页面效果：目标、动作、完成后观察、结果读取和恢复探针。`click`、`scroll`、`read` 是该能力配置中的动作，不是节点类型。一次能力调用可以执行少量底层 BrowserSkill 命令，但必须共同完成一个外部可观察效果；它不能接受任意命令数组，也不能成为隐藏脚本解释器。

### 3.3 任务数据层

以下内容只保存在版本化任务、链输入或能力配置中：

- 站点与入口 URL；
- 页面控件名称和稳定定位；
- 业务字段、数量、筛选条件和去重键；
- 点击下一页还是滚动、弹框是否存在、结果字段如何读取；
- 站点级保守频控参数。

公共 contracts/runtime 不识别电商、评论、商品、剧集、表单等业务概念。

## 4. 节点输入输出契约

### 4.1 capability

输入是具名绑定，配置是 JSON 值并由注册能力二次校验。成功输出必须符合 `outputContract`。标准出口为：

```text
success | missing | timeout | blocked | human_required | failed | cancelled
```

浏览器能力成功时还要返回新鲜浏览器状态。需要人工登录、验证码或一次性确认时返回 `human_required`，运行器在同一运行上保存检查点并等待用户；恢复时先执行能力声明的状态探针，再决定继续、重做只读步骤或因不确定副作用暂停。

### 4.2 llm

输入由绑定产生，输出由明确合同校验。节点必须保存 instruction、model、timeout 和允许调用次数。每次调用先记录意图，再记录完成、失败或中断及供应商报告的实际调用数。结构化输出不符合合同走失败出口，不把旧结果当作本次输出。

### 4.3 branch

只读取已有值并执行确定性判断。标准出口为 `true | false | failed`。判断表达式沿用受限 predicate，不执行脚本。

### 4.4 loop

循环是组合节点，拥有一个内部子图。它必须声明：

- `each` 或 `while`；
- 最大迭代次数；
- 当前游标和稳定来源键；
- 每轮输入绑定；
- 累计值、去重键与停止条件；
- 单项失败策略；
- 循环体入口和出口。

循环状态必须可序列化到检查点。恢复继续同一运行，已完成稳定键不重复处理。无新增数据、停止条件满足或输入耗尽走 `done`；达到上限走 `limit`；循环体本身只保存一份。

### 4.5 invoke

保存被调用链的固定 id、version 和 digest，以及单次或逐项调用规则。逐项调用必须有稳定键、最大项数和失败策略。每项创建独立 invocation，但仍属于同一个产品运行和同一个浏览器控制会话。

### 4.6 terminal

终点直接绑定链输出和证据，并声明 `completed | partial | blocked | failed | cancelled`。它取代单独的 emit 节点；运行器到达终点时完成输出合同校验并保存最终结果。

## 5. “打开评论并继续收集”的具体沉淀

这类任务使用 4 个节点实例、3 种节点类型：

```text
capability：打开目标区域，确认弹层出现，读取第一批数据
  -> loop：保存第一批，按稳定键去重，判断数量/无更多内容/上限
       -> capability：执行下一页或滚动，确认内容发生变化，读取新增批次
       -> 回到 loop
  -> terminal：返回累计结果和完成证据
```

两处 `capability` 都调用 `browser.perform@1`，区别只在任务配置。平台没有“打开弹窗节点”“评论节点”“翻页节点”或“下滑节点”。如果弹层打开后第一次读取与后续翻页完全相同，也可以把首次读取放进循环，把链收敛为 3 个节点实例；是否合并由可验证效果和恢复边界决定，不由页面动作名称决定。

## 6. 从成功探索到稳定链

任务先划定链路边界，再做代表探索。计划调用有三种通用方式：

- `once`：链只调用一次，代表探索取得完整单次结果；
- `each`：集合项彼此独立，链按项调用，代表探索只处理第一项；
- `batch`：需要跨项累计、去重或按结果停止，整份集合只调用一条带 `loop` 的链，代表探索仍只执行第一项以取得循环体证据。

`batch` 解决“必须检查后才知道是否计数”的通用问题。例如从列表得到候选后，是否纳入、稳定结果键和何时达到数量上限都由循环每轮真实输出决定。发现链只收集有序公开目标，不为了下游筛选而反复进入详情；正式复跑时，循环在达到业务结果数量、输入耗尽或风险阻断时停止。

编译分为五步：

1. **筛选证据**：只使用成功预执行中被结果来源或完成条件引用的事件；失败探针留在审计，不进入复跑图。
2. **形成语义片段**：把相邻且共同完成一个可观察效果的浏览器事件归为一个片段，例如“打开区域并取得首批值”。
3. **识别重复结构**：相同动作骨架、相同输出形状和稳定进度证据形成一个 `loop`，不复制事件。
4. **生成最小节点数据**：模型只补充片段用途、动态绑定、重复边界和输出来源；宿主生成 id、边、错误出口、预算、布局和合同校验。
5. **确定性物化**：相同轨迹、注解和合同必须产生相同可执行摘要；原始 event id 不得直接成为公共 node id。

节点数量由语义步骤和控制结构决定。增加同构翻页次数只能增加轨迹证据和运行预算，不能增加链节点数量。

若编译器无法证明多个事件属于同一个可验证效果，宁可保留两个通用 capability 节点；不得退回逐事件回放，也不得让模型直接输出完整 Chain IR。

## 7. 运行、检查点和恢复

- LangGraph `StateGraph` 继续负责异步推进、循环调度、取消和递归上限。
- `TaskChainRuntime` 只负责 IR 映射、预算、幂等键、能力调用、浏览器恢复核验和运行审计。
- 每个产品运行只占用一个真实 BrowserSkill 会话；子链和循环复用该会话。
- 每次能力调用完成后保存运行状态；外部写操作在调用前保存 pending effect。
- `human_required` 自动形成等待点。真实验证码只等待用户，不绕过、不自动重试。
- 检查点恢复必须核验浏览器标签、URL 和观察摘要。不能确认外部副作用是否完成时保持暂停。
- 输出只在 terminal 完成时发布，未通过输出合同不能标成 completed。

## 8. 访问频控与失败分类

所有预执行、样本复跑、修复验证、换输入验证和正式复跑共用持久来源访问门。可注册域共享访问压力，等待时间不计入浏览器活动预算。

错误分类必须区分：

| 事实 | 处理 |
| --- | --- |
| 本地授权来源不允许，即 `origin_denied` | 本地失败；不得写入站点冷却，不得伪装成人工验证 |
| 站点明确限流或带 `retryAt` | 持久硬冷却并暂停同站点动作 |
| 站点认证或验证码 | 保存现场并等待用户 |
| 站点拒绝访问 | 持久冷却并暂停 |
| 定位、绑定、输出或完成条件错误 | 使用原证据生成新链版本，再做一次样本验证 |
| 网络结果不确定 | 暂停并保留 pending effect，不盲目重复 |

本地策略错误和外部站点事实不能共用一个熔断码。

## 9. 数据迁移

已经持久化的旧链和旧运行保持原字节、原版本和只读审计。新编译链写入新的稳定节点模型标识。旧链不得静默改写成新模型；只有基于已保存成功预执行证据重新编译并通过验证，才生成新链版本。当前 94 节点候选不作为新实现夹具，也不作为迁移模板。

## 10. 实施阶段

### I1：冻结契约与失败用例

- 新增稳定节点模型及能力引用合同；
- 为旧链保留只读解析边界；
- 添加“事件数增长但节点数不增长”的编译失败用例；
- 添加 `origin_denied` 不写站点冷却、不进入人工等待的失败用例。

通过门：用例在旧实现上失败，且失败原因正好命中两个缺陷。

### I2：运行时与浏览器能力

- 增加能力注册与通用调度；
- 把现有 browser、observe、data 行为收进能力实现；
- 把 branch、loop、invoke、llm、terminal 接入现有运行状态；
- 把人工等待、检查点和输出发布移到运行生命周期；
- 保留显式模型审计和外部副作用恢复规则。

通过门：contracts、runtime、browser 所属最小测试和类型检查通过；普通链模型调用数为 0。

### I3：语义编译

- 以成功轨迹生成语义片段；
- 折叠有界重复区域；
- 生成 capability 配置、内部循环体和 terminal 输出；
- 删除逐事件 observe/checkpoint 扩张路径；
- 拒绝无法证明来源、恢复或循环边界的候选。

通过门：同一语义流程不同事件数量生成同构图；评论弹层场景节点数固定；相同输入编译摘要稳定。

### I4：编写和修复闭环

- 先生成少量步骤的计划，再按 `once`、`each` 或 `batch` 只探索各步骤代表输入；
- 自动执行一次样本复跑；
- 只对本地编译/定位/绑定/输出错误生成新版本；
- 外部限制与验证码暂停；
- Workbench 只展示稳定节点和真实运行证据。

通过门：修复不重跑预执行，不改写旧链；失败链不会标成 verified。

### I5：本地验证与真实复跑

本地仅运行覆盖本轮不变量的 package 测试和类型检查，不运行根级全量测试。通过后：

1. 核对 BrowserSkill doctor、活动会话和来源冷却；
2. 审计新链节点数、能力配置、循环边界和显式模型节点；
3. 只用一个真实会话做一次低频代表输入样本复跑；
4. 本地错误修复后最多再跑一次；外部限制立即停；
5. 样本通过后，等待访问门再用不同输入验证一次；
6. 保存运行、访问间隔、浏览器会话回收和模型调用审计。

## 11. 本轮验收标准

- 新链只有 `capability | llm | branch | loop | invoke | terminal` 六种公共节点。
- 浏览器 click、scroll、read 和数据处理不再是节点类型。
- 同构重复不会增加节点数量，循环体只保存一份。
- 普通节点无法隐式调用模型；所有模型调用都有显式节点与审计。
- `origin_denied` 不写站点冷却，也不要求用户处理验证码。
- 公共源码不含站点或电商业务概念。
- 旧 dirty checkout 的用户改动全部保留；不创建分支或 worktree，不推送。
- 本地最小验证先通过，随后才有最少次数的真实 BrowserSkill 证据。

## 12. 2026-09-14 实施与当前证据

当前真实任务复核发现一项阻断性实现缺口：文档已要求循环“按真实结果停止”，但现有
`append_unique` 会无条件累计每轮结果，`each` 循环也只会在输入耗尽或迭代上限时结束。
因此，候选需要现场判定、部分候选不计数且达到目标数量应立即停止的任务，仍可能多访问页面，
也无法用运行时事实证明目标数量。修复必须保持通用：累计器按受限 predicate 决定是否接纳，
循环按累计数组长度与动态输入上限停止；任务字段只作为 binding 数据，不进入公共节点类型。

已完成：

- 新链只写入 `stable/v1`，公共节点收敛为六类；历史 11 类节点只读兼容，旧链不静默迁移。
- `browser.perform@1` 在一个能力节点中完成动作和动作后采集；`data.transform@1` 承担通用数据变换。
- `loop` 保存可序列化游标、已完成稳定键和 `append_unique` 累计值；LangGraph 继续负责图推进。
- 计划增加 `batch`：整份集合只调用一条链，链内必须有一个显式循环；`each` 仍是一项调用一次同一链。
- 计划先于浏览器探索；发现步骤只收集可见目标，不能为了下游字段提前逐项打开详情；代表探索只处理第一项。
- 编译器只从成功且被结果引用的轨迹生成语义节点，动作与紧邻读取合并；三项以上同构映射没有循环时拒绝候选。
- 候选自动执行样本验证；本地失败最多修复一轮，复用已有轨迹；外部认证、验证码、限流和拒绝访问直接暂停。
- 访问门按可注册域持久计量；`origin_denied` 保持本地失败，不写入站点冷却。
