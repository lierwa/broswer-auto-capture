# 日常 Chrome 以任务专属窗口作为默认控制边界

2026-10-01 用户明确选择“仅任务专属窗口”。B-A-T 使用用户原来的日常 Chrome/Profile，并为任务建立独立可见窗口；用户个人标签页不自动进入控制范围。任务窗口中的页面仍需要可证明的任务所有权，不能仅凭窗口号相同或标签页被手动移动就取得授权。

这一选择保留日常浏览器环境，同时避免持久连接授权被解释为对整个 Profile 的常态控制。页面、事件与资源清理均需执行同一所有权边界；具体 relay 组件仍待真实兼容验证，本文不冻结技术选型。

实施证据（2026-10-01）：固定微软受管扩展在独立测试 Profile 的同窗口/拖分组真实反例通过；宿主原 TargetScope 与扩展原目标映射共同执行既有边界。运行/持久授权通过限定消费者样本，来源与适配见 RESEARCH 最新节；本文不扩大个人页权限，也不替代实际日常 Profile 或 Windows 实机准入。

补充证据（2026-10-02）：实际日常Chrome154已完成首次配对、保存授权复用及合成页面的原W-U/LangGraph普通运行，0模型、清理确认；未读取个人页、复制Profile或关闭用户Chrome。此次connect.html的loopback资源声明修补不改变本ADR的窗口/页面所有权；实际Profile拖入反例与Windows仍未测，独立134样本的边界证据不扩大为这些结论。

补充证据（2026-10-02窗口回归修复）：B-U内部焦点不等于实际Chrome页面激活。现复用原Target.activateTarget，只激活租约已记录且TargetScope核验的本operation目标；激活失败使用原清理路径，不取得个人页或Chrome进程所有权。原V5从工作台完整复跑通过，0模型、清理确认；所属新/复用连接与失败清理回归通过。该修补落实既有任务窗口行为，没有新增产品或架构决定，双平台/冷启动等未测边界不变。
