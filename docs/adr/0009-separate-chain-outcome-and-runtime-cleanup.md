# 区分链路运行结论与运行资源清理

## 背景

一次正式复跑中，不可变链路的所有节点和 `TaskRun` 已经成功完成，但 runner 在 `finally` 清理时以非零退出码结束。外层通用异常路径把它改写成“确定性、可模型修复的链路失败”，结果页因此失去普通再次运行入口。这说明系统把三种不同事实压进了同一个最终异常：链路做了什么、正式 execution 是否已经闭合，以及 execution 拥有的运行资源是否释放。

## 决策

B-A-T 将链路运行结论、正式执行生命周期和运行资源清理结论视为相关但不同的事实：

- `TaskRun` 记录不可变链路沿实际控制流发生的节点、输出和终点；close 失败不得重写这些事实。
- `TaskExecution` 编排计划步骤，并在全部所属资源完成清理后闭合。
- 资源清理单独记录 runner、浏览器会话和临时资源是否得到释放确认。

链路已经合法完成而资源清理尚未确认时，execution 进入 `cleanup_required`，保留已完成步骤和业务输出，并只提供“核验并清理资源”。它不得产生确定性链路失败、链路修订或模型修复授权。清理确认后，同一 execution 从 `cleanup_required` 闭合为 `completed`；清理尝试和原始异常作为追加审计保留。

上游 runner 的 close 必须返回经过校验的结构化清理报告，不得以一个非零退出码覆盖已经返回的业务结果。若业务执行与清理同时失败，业务错误保持主错误，清理错误作为独立生命周期事实。任何恢复操作只能作用于本次 execution 明确拥有的进程、浏览器和临时资源；不能按进程名清理、连接用户日常浏览器或删除持久 Profile。

旧记录缺少结构化清理事实时保持只读兼容。可以通过实际资源核验追加清理结论，但不得把错误字符串匹配作为新运行的状态机。

## 后果

- 新正式 execution 必须持久化结构化 cleanup 状态和追加清理审计。
- 产品需要 `cleanup_required` 状态及幂等的“核验并清理资源”操作。
- 成功链路不会被清理异常冒充为链路缺陷，真实资源占用也不会因为业务已完成而被忽略。
- 同一 execution 可以在不调用模型、不改写链路版本和历史运行的情况下恢复到可再次运行。
- 代价是多保存一个生命周期事实，并对重启恢复、资源所有权和并发清理增加明确合同。
