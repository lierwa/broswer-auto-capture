下文保留此前阶段决策和实施事实；其中“新采集默认关闭后离线首编译”的要求由本段替代，其余来源、验证、发布及安全约束继续有效。

## 决定

主线固定为：**唯一已确认准备草案 → 同版确定性技术投影 → 单 Browser 代表采集 → 每次采集的一份不可变来源 → 显式离线编译 → 自动样本与独立复验 → 用户手动发布 Release → 独立正式 Run**。这细化 [ADR 0011](0011-interview-produces-preparation-draft.md) 的草案交接，并服从 [任务链架构基准](../development/TASK_CHAIN_ARCHITECTURE.md)。版本化任务数据保存网站、字段、范围和数量；公共源码不增加站点或任务类别规则。

第 1 步先切断采集与编译的同一响应。Python author 只返回 `{ output, canonicalRequest, sourceGaps }`。`canonicalRequest` 由现有 Python 规范化序列化生成，完整保留真实 trace、request 的数值及来源引用；`history`、技术性的 `sourceSuccess` 与浏览器命令数从 trace 派生，不再由模型或两份响应各自声明。`sourceSuccess` 只表示原生代表执行的技术终点，不能代替业务范围证明。来源内没有 `compilerResponse`，也不把编译候选当成采集事实。

TS 在收到 JSON 响应时为该次代表采集**先保存一次**不可变 `source/v3` 原文，状态为 `received`；随后才校验采集合同与同版身份。校验拒绝时，这份原文仅供诊断，不能进入编译。Browser owner 的关闭结果另记在本次 job 的来源引用；只有合同和身份通过、关闭已确认的来源才能进入显式离线编译。恢复时重读同一 `source/v3`，严格解析新三字段并核对身份和摘要。编译复用已有 workflow-use 编译器，在没有 Browser 控制会话的阶段生成独立的编译产物或明确缺口。编译失败保留来源和失败事实，不自动开启新 Browser、从旧失败任务寻找来源、改写来源或把同版第二次成功称为首次通过；确需重新采集时由工作台明确发起新 job，并保留两次历史。

旧 `source/v2`、`received-source` 与旧模型业务计划只供历史查看；新主线不解析它们来生成计划、编译或恢复执行，也不提供执行兼容层。现有 SQLite 历史记录保留原样，不删除、不迁移成新来源。`received-source` 的重复写入热路径随 `source/v3` 合同落地而移除。没有通过新来源合同、owner 关闭未确认、结果缺少真实读取引用时，不进入候选编译或发布门。

## 采用与排除

2026-09-27 补充：第 2 步不能缩减成修改 done 字段名。当前最终值倒推 DOM、单次读取与最终数量耦合、自然编译仅生成顺序链是三个独立断点。必须先闭合方法与真实读取引用，再连接已有循环运行能力；代表样本不能充当最终业务全集。先补系统能力及所属定点验证，随后再跑全新产品任务。

继续复用 browser-use 的 Agent/Browser、受管 workflow-use 编译器、Pydantic/Python 规范化序列化、Zod 边界、SQLite artifact 和 LangGraph 运行调度。B-A-T 只负责草案版本与来源身份、跨语言合同、不可变产物、输入输出绑定和审计。一个产品运行只有一个浏览器控制会话；普通复跑不隐式调用模型，只有显式 `llm` 节点可调用模型。

不再把含 `compilerResponse` 的复合响应当成来源，也不为同一采集同时写 `received-source` 与正式来源两份活跃权威。历史 `source/v2`、旧计划和失败任务不会被自动挑作后续编译输入；编译缺口只从显式指定的同版 `source/v3` 定位。重新让 B-U 碰运气不是编译阶段的恢复动作。敏感页面内容和 Profile 不进入 Git 或普通日志，来源仅保存在任务私有受管存储。
