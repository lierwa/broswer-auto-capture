# 区分需求、准备、运行完成与用户验收

2026-09-25 补充：[ADR 0011](0011-interview-produces-preparation-draft.md) 明确需求对话直接形成并确认唯一准备计划草案，确认后交 B-U；本 ADR 对真实页面试做、正式运行完成与用户验收的分层仍适用，不再意味着确认后还要独立生成一份业务计划。

B-A-T 将需求对话、任务准备、正式运行和用户验收视为四个不同阶段：需求对话必须由用户确认所有会改变结果的重要歧义，并可用只读搜索解决来源候选；搜索词及原始结果的业务语义由访谈 LLM 判断，宿主只执行受限搜索、校验候选引用并持久化用户确认，不建立关键词或打分式来源 judge。任务准备只研究真实网页上的实现方法；正式运行在不可变链路按合法控制流结束且没有节点、合同或运行时错误时即为完成；结果是否符合用户预期由用户验收，不再由链路结束后的全局语义 judge 改判。局部不符合预期通过自由画布建立链路修订草稿并发布新版本，整体目标不对则携带运行记录返回需求对话形成新需求版本。这样既避免模型填充复杂完成证明合同和正常执行后的假失败，也保留不可变版本、真实错误、人工等待、普通复跑零隐式模型调用和用户可控修订。

实现上，准备阶段关闭 browser-use 的全局 judge，只保留 Agent 正常结束、结构化输出合同和来源证据；出现 `confirm_intent` 编译缺口时形成持久化需求回流。正式运行到达 completed terminal 后不再执行 chain/step/plan 的链尾 predicate 二次改判，完成证据指向实际 terminal；目标定位、动作派发、输入、读取、输出、浏览器、人工等待、取消和预算错误仍按各自真实边界处理。旧 trace 与 artifact 只读兼容，不改写历史，也不把旧 `judged` 字段恢复为新门。
